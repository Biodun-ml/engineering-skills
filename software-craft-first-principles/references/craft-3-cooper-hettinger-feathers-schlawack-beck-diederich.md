# craft-3 — cross-cutting principles

1. **Coupling is the core cost driver.** Two elements are coupled with respect to a change if changing one forces changing the other; the total cost of software is dominated by rare, cascading changes caused by coupling (power-law, avalanche-like). Decide coupling vs decoupling as an explicit trade-off. [Beck, Tidy First?; Cooper, TDD; Schlawack, Design Pressure; Abramov, WET Codebase]
2. **Test behaviour through a stable public contract, not implementation details.** The trigger for a new test is a new requirement, not a new method. Test at the module's API/ports; keep internals free to change. [Cooper, TDD; Feathers, Legacy Code; Abramov, WET Codebase]
3. **The "unit" is the test's isolation, not the class.** Avoid shared fixtures and slow tests; don't mock collaborators just to isolate a class. Mock only at expensive/external boundaries. Over-mocked tests freeze design and sometimes test only the mocks. [Cooper, TDD]
4. **Red, dirty green, refactor, with no new tests during refactoring.** Get to green fast with ugly code (finding the solution and engineering it are separate jobs), then clean up with safe, behaviour-preserving moves; introduce patterns only now. Probe tests for internals are temporary: delete them. [Cooper, TDD]
5. **Test pain is design feedback.** Hard-to-test code is badly coupled code; widening test scope (all end-to-end) hides that pain; monkey-patching is "software bankruptcy". Fix the design and you get better tests too. Avoid "test damage". [Feathers, Legacy Code; Schlawack, Design Pressure]
6. **The shape of the data shapes the code: reshape at the edges.** Parse, validate and *convert* external input (API payloads, DB rows, files) into types built for your problem at the boundary, so the core is simple and IO-free. Don't let the API schema, the DB schema or a compromise between them become your domain model; explicit mapping between duplicate-looking per-layer types is fine. [Schlawack, Design Pressure]
7. **Make illegal states unrepresentable:** separate types per state (open/paid/overdue invoice; per-country address) instead of one blob of optional fields. Classes full of `| None` are a major smell. [Schlawack, Design Pressure]
8. **Duplication is far cheaper than the wrong abstraction.** When a shared abstraction starts collecting special cases and parameters, inline it back into callers; re-extract later only once cases prove genuinely identical. Test concrete features, not abstractions, so inlining stays possible. [Abramov, WET Codebase; Metz via Schlawack]
9. **Don't build speculative structure.** A class with `__init__` plus one method is a function; empty base classes, one-off custom exceptions, deep package taxonomies all cost every future reader. Use built-in data structures (dict/set) and stdlib exceptions until a real need appears. Code is a liability; ship features, not lines. [Diederich, Stop Writing Classes]
10. **Easy is not simple.** Familiar shortcuts (raw dicts everywhere, god classes, DRY at any cost, fewer keystrokes) are *easy*; simple means not interleaved/coupled and usually takes harder thinking. Interrogate KISS/YAGNI/DRY slogans; every `if` doubles code paths. [Schlawack, Design Pressure; Abramov, WET Codebase]
11. **Tidy first (usually, briefly), and never mix structure and behaviour changes in one change.** Split tidying commits from feature commits; at the macro level they interleave continuously. Design is an ongoing activity, not a phase or a six-month freeze. [Beck, Tidy First?]
12. **Use parallels to make design change interruptible:** old and new coexist (add new param/field/path, migrate callers, delete old), each step deployable. [Beck, Tidy First?]
13. **Design economics: survival, NPV, options.** Defer design decisions that can wait (spending later = spending less); invest in structure that creates options (worth more under uncertainty); early on, optimise for the software surviving at all. Structure improvements can unlock "jackpot" features once something becomes cheap. [Beck, Tidy First?]
14. **Invest where change is concentrated.** Value, bugs and commits follow 80/20; harden hotspots (frequently changed, bug-prone, critical code), only stabilise stable-but-ugly areas. Mine git history. [Feathers, Legacy Code]
15. **Legacy = code you can't confidently understand or change.** Build confidence via tests as tripwires, the type checker ("lean on the compiler"), deliberate breakage, and firewalls against non-local effects (inject dependencies instead of touching globals/singletons). Scratch-refactor a throwaway copy to learn unfamiliar code. Dependency-breaking may look ugly; that's fine. [Feathers & Clausen, Legacy Code]
16. **AI-generated code still has to be understood and verified by you;** code remains the representation language, AI output is "generate and test", and cohesion/coupling still matter at coarse grain. [Feathers, Legacy Code; Schlawack notes AI makes keystroke-saving arguments moot]
17. **Idiomatic Python is clearer *and* faster:** iterate directly (`enumerate`, `zip`, `reversed`, key functions, two-arg `iter`, `for/else`), use `dict.get`/`defaultdict`/`Counter`/`ChainMap`/`deque`, `''.join`, tuple unpacking for simultaneous state updates, keyword args and named tuples for readable calls/results, generators to avoid materialising data, decorators (`lru_cache`) and context managers to separate admin logic from business logic. [Hettinger, Idiomatic Python]
18. **One logical line = one thought.** Neither cram nor split a single idea into "subatomic particles"; prefer declarative expressions that state what you want. [Hettinger, Idiomatic Python]
19. **Teach and adopt practices with their trade-offs and context**, not as flattened best practices; and change team habits by visibly doing better work, not preaching. Design is ultimately about human relationships: align authority with responsibility when your changes create work for others. [Abramov, WET Codebase; Feathers, Legacy Code; Beck, Tidy First?]

## Ian Cooper — TDD, Where Did It All Go Wrong (https://www.youtube.com/watch?v=EZ05e7EMOLM)
**Test behaviours through a module's stable public contract, never implementation details; the "unit" in unit test is the test's isolation, not the class.**

- **The problem he saw (from ~10 years of TDD):** test suites 2-3x the size of production code; teams 20-50% slower; refactoring (changing shape, not behaviour) broke dozens of tests, almost always the heavily mocked ones that asserted "call X twice, then Y with these args". Tests that are red with nobody knowing what they check get deleted. Mock-heavy tests sometimes test only the mocks. Customer-facing acceptance suites (FitNesse, SpecFlow/Cucumber) were red most of the iteration, slow, unread by customers, and spawned a "who broke the build" blame role. If a team keeps pushing back on a practice, it is a signal the practice is wrong, not that they "don't get it".
- **Root cause:** the trigger for a new test became "I'm adding a method to a class". In Kent Beck's original TDD book the trigger is "I have a new requirement/behaviour". Tests should be written against the API = the exported surface of a module (its facade/ports), which is stable; the implementation behind it is unstable and should stay free to change.
- **Unit of isolation is the test.** Beck's "unit test" meant tests that do not affect each other when run in any order. It does not mean isolate a class from all collaborators with mocks. You avoid DBs/files in tests only for (a) shared-fixture problems (one test's rows leak into another) and (b) speed (suite should run in a couple of minutes). If neither applies, touching a DB or file system in a developer test is fine. Use a fresh in-memory DB per test if sharing is the problem.
- **Red-green-refactor, done properly:**
  - Red: prove the test can fail (there are no tests for tests; an always-passing test proves nothing).
  - Green: get it passing as fast as possible, committing any sins: transaction-script style, line after line, copy from Stack Overflow. You cannot both discover the solution and engineer it at once; trying causes over-engineering or analysis paralysis. "For this brief moment speed trumps design."
  - Refactor: now make it clean, driven by removing duplication and Fowler's code smells. This is the right time to introduce design patterns (Kerievsky), because you now know the real solution. **Write no new tests during refactoring**: refactorings are safe, behaviour-preserving moves already covered by the behaviour test. Extracted classes/helpers stay internal and untested directly. Use coverage to spot speculative new conditionals; a genuinely new branch means a new behaviour, which needs a new test.
- **Refactoring definition:** changing implementation without changing the public interface. Renaming a public method on a public class is not refactoring (you don't know its callers).
- **Ports and adapters (hexagonal/clean/onion):** domain core is plain objects with no tech concerns; adapters (HTTP framework, GUI, DB, message queue, email) at the edges; ports are the doors between them (facades/command handlers on the inbound side, repositories etc. on the outbound side). Developer tests drive the ports. Integration tests only check adapters are wired/configured correctly; don't unit-test adapters (that's third-party code). A few system tests from the outside in. Aim for a testing pyramid, not the inverted "ice-cream cone" of manual + Selenium tests, which break on cosmetic UI changes, run overnight, and create blame games.
- **Gears:** normally "fourth gear" (test the API, dirty green, refactor). "Fifth gear": implementation is obvious, write the clean version directly (watch coverage, if it drops you're writing speculative code). Shift down when you don't know how to go green: write small tests that probe implementation details to feel your way, then **delete them** afterwards; they protect your choices and burden the next person.
- **Mocks:** useful when a resource is expensive or a shared fixture; also when a refactor reveals a genuinely new public dependency (another module's API you haven't built yet). Don't use mocks to isolate classes, or to police how juniors implemented a method; that over-specifies software and freezes design. Don't expose internals (e.g. InternalsVisibleTo, making things public) just to test them. If you register an IoC container in a test, something is wrong.
- **ATDD/BDD-tool suites:** Beck, and James Shore (FIT author) dropped them; customers don't read them and they cost a lot. The real fix is to make developer tests behaviour-focused, written in the code's own language, informed by talking to customers. Dan North's original BDD insight was the same: swap "test" for "behaviour".
- **Coupling is the killer, more than duplication.** Decoupling tests from implementation is what makes refactoring actually possible.

**For Sam:** for a provider integration (Viator/RateHawk), test at the port: "given this supplier response, search returns these normalised offers / booking produces this state". Fake the HTTP adapter at the boundary, not every internal helper. For data scripts, test the pipeline's public functions on small fixture frames (input rows -> output rows) rather than each private helper; then you (or the AI) can rewrite internals freely. When AI generates throwaway probe tests to figure something out, delete them once the behaviour test passes.

## Raymond Hettinger — Transforming Code into Beautiful, Idiomatic Python (https://www.youtube.com/watch?v=OSGv2VnC0go)
**Stop writing C/Java in Python: use iterators, the right built-ins and data structures, and code that says *what* you want in one unit of thought. It is shorter, clearer and usually faster.**

(note: talk is from 2013 / Python 2. `xrange`, `izip`, `iteritems` became `range`, `zip`, `items` in Python 3, all lazy views/iterators. `ignored` shipped as `contextlib.suppress`; `cache` exists as `functools.lru_cache`/`functools.cache`. `contextlib.redirect_stdout` shipped.)

- **Mental model: Python's `for` is "for each".** It walks collections via the iterator protocol; it is not a counter loop. Manipulating indices by hand is almost always a smell. People write index loops because they drift back to the idioms of their first language.
- **Loop idioms (grep your codebase for the "before" form and replace):**
  - `for i in range(len(xs)): xs[i]` -> `for x in xs`.
  - Backwards: `reversed(xs)`, not a count-down index loop.
  - Need index too: `enumerate(xs)`.
  - Two collections at once: `zip(a, b)` (lazy in Py3; in Py2 `zip` built a third list, which wastes memory and falls out of CPU cache. A cache miss can cost ~400-600 cycles vs half a cycle, ~2.5 orders of magnitude).
  - Sorted: `sorted(xs)`, `reverse=True`. Custom order: use a **key function** (called once per item, e.g. 1M calls) not a comparison function (n log n calls, ~20M for 1M items). SQL gets by with ORDER BY keys, so you can too; Py3 removed cmp.
  - Sentinel-based APIs (`f.read(32)` until `''`): `for block in iter(partial(f.read, 32), '')`. Once something is an iterable it plugs into `sorted`, `set`, `sum`, `min/max`, `heapq`... The sentinel style is fragile (story: the "Quito" claim stopped a punch-card job whose stop code was QUIT).
  - Multiple loop exits: `for ... else` replaces a `found` flag; read `else` as "no break". (Knuth's idea.)
- **Dictionaries:** the core tool for linking, counting, grouping.
  - Iterate keys with `for k in d`; iterate `list(d)` / `d.keys()` copy if you are mutating while looping (mutating while iterating is always a bug).
  - Keys and values: `for k, v in d.items()`, not `d[k]` lookups (rehash per key).
  - Build from two lists: `dict(zip(keys, values))`.
  - Counting progression: `if k not in d: d[k]=0; d[k]+=1` -> `d[k] = d.get(k, 0) + 1` -> `defaultdict(int)` / `Counter`. Teach beginners the basic form first.
  - Grouping: `groups = defaultdict(list); groups[key(x)].append(x)`; change only the key line to group by anything. (`setdefault` is the older idiom.)
  - `popitem()` is atomic, usable across threads without a lock.
  - Layered config (defaults < env vars < CLI args): `ChainMap(cli_args, os.environ, defaults)` instead of copying and `update`-ing dicts (copying is slow).
- **Clarity over microseconds:**
  - Keyword arguments at call sites: `search('obama', retweets=False, numtweets=20, popular=True)` instead of `search('obama', False, 20, True)`. Costs a hair of speed; saves hours of programmer time. Skip only in tight loops. Great onboarding exercise for a new codebase.
  - `namedtuple` for return values (`TestResults(failed=0, attempted=4)` vs `(0, 4)`); still a tuple so substitutable. (Today: also `dataclasses`/`typing.NamedTuple`.)
  - Unpack sequences: `name, age, email = rec` not `rec[0], rec[1]`.
  - **Simultaneous state updates:** `x, y = y, x + y`. Updating state across several lines leaves it mismatched mid-way and order-sensitive. Classic bug: in an orbit or mortgage simulation, updating `principal -= payment` before computing interest. Spreadsheet users get this right because each row refers to the previous row; tuple assignment gives you that model.
- **Efficiency rules:** don't move data needlessly. Build strings with `''.join(parts)`, not `+=` (quadratic). `del xs[0]`, `xs.pop(0)`, `xs.insert(0, v)` on a list are O(n) and signal the wrong structure; use `collections.deque` (`popleft`, `appendleft`). His consulting trick on slow million-line codebases: grep for exactly these three.
- **Decorators and context managers separate admin logic from business logic:**
  - Caching mixed into a fetch function -> `@cache`/`@lru_cache` on any pure function (same input -> same output). Keep a utils module of small reusable tools like this.
  - Repeated setup/teardown -> context manager: `with open(...)`, `with lock:` (never forget release on error), `with localcontext() as ctx` for decimal precision, `with suppress(OSError): os.remove(f)` (checking `exists` first is a race condition), `with redirect_stdout(f)`.
  - Spider-Man rule: these act like macros, so names must be very clear, or they hide awful actions.
- **One logical line = one English sentence.** Don't cram, but don't split a single thought into "subatomic particles" either. `sum(i**2 for i in range(10))` is declarative (what you want) vs an accumulator loop (how to do it). Generator expressions avoid materialising a list.

**For Sam:** for million-row scripts: stream with generators/iterators instead of building intermediate lists; group/count with `defaultdict`/`Counter`; `deque` for queues; `''.join`; config via `ChainMap`; `@lru_cache` on pure lookups (e.g. geocode/normalise functions called repeatedly); `with` for files, DB connections, HTTP sessions. Ask AI-generated code reviews to check exactly this list. Note that in pandas/DuckDB-heavy code, vectorised operations beat any Python loop idiom; these idioms matter in the glue code and pure-Python pipelines.

## Michael Feathers & Christian Clausen — Working Effectively with Legacy Code (GOTO 2023 interview) (https://www.youtube.com/watch?v=P_6eDL1aqtA)
**Legacy code is code you can't confidently understand or change; get control by building test "sensing" and effect-firewalls around the high-value, high-change 20%, and treat test pain as design feedback.**

- **What "legacy" means:** subjective. Classic definitions: code from someone else; Feathers' famous one, code without tests (working without a safety net is qualitatively different). His current emphasis: how well you *understand* its behaviour and how often it *surprises* you. Clausen's framing: confidence, which can come from tests, types, naming and structure without reading every line (humans read code slowly; good names and hierarchy let you skip branches). One counterintuitive surprise in a codebase makes you ask "what else is here?".
- **The core danger: non-local effects.** Local changes having global effects is what makes legacy code scary; humans think locally. Effects propagate through exposed data, constructor/argument passing, and direct mutation (globals, singletons). Work before writing tests is building **firewalls**: e.g. inject a value through the constructor instead of a class reaching into a singleton. Where globals are too pervasive to remove in your lifetime, at least add tests as tripwires so you learn immediately when something breaks.
- **Sources of confidence beyond tests:**
  - "Lean on the compiler": change a signature and let type errors list every call site. In Python, a type checker (mypy/pyright) plays this role.
  - Deliberately introduce errors to see what breaks: a form of testing for understanding behaviour.
  - Writing a test is asking the codebase a question. If a question is hard to ask, the design is telling you something.
- **Testability and good design are the same thing** ("deep synergy"): almost every pain in testing points to a design problem (Clausen: same with types; if you need casts/reflection, the design is off). Design should let you query behaviour at several levels: a few core computation methods you can test directly, a domain-level API for bigger questions, end-to-end for whole-system ones. Code should be no more complex than the domain it models.
- **Breaking dependencies looks ugly; do it anyway.** Techniques that get tests in (loosening encapsulation at a seam, shipping test hooks) may offend design taste, but they enable the refactoring that improves design. "Best is the enemy of good." Break encapsulation selectively, at the edge of a *new* boundary you are forming around something valuable. Sometimes group three things into a bigger unit; sometimes split one thing with many responsibilities and support it from outside with tests while you split it.
- **Don't over-valorise tests.** Structurally coupled tests block refactoring. Feathers is willing to "park" some tests, do a structural refactor with confidence from other means, then rewrite tests against the new structure. Avoid one-test-class-per-production-class; grow tests from one entry point and refactor outward so tests cover a larger area (agrees with Ian Cooper). Languages lack a "published vs merely public" distinction; you must decide which interfaces you hold invariant. Clausen: the hardest practical testing skill is learning to stub correctly.
- **Pareto everywhere: value and change are not uniform.** Method sizes, bug density and commits follow 80/20 distributions as a side effect of incremental growth. Many files will never change again. Invest in hotspots: frequently changed, bug-prone, business-critical areas. A messy but stable area: understand and stabilise it, but don't polish it, there is no return. Improvements in hot areas pay back almost immediately because the next change benefits. You are not doomed by a 10,000-file codebase; you only need the active nuggets. Tools: CodeScene (hotspots, knowledge-loss if someone leaves), SonarQube; git history itself is a goldmine.
- **Rules of engagement:** critical areas get stricter process (specific reviewers, PRs); low-criticality areas can be open. Watch for Conway's-law fault lines; Team Topologies is useful but think about forces, not just prescriptions. Build a refactoring culture: discuss it in retros, refactor together, help devs see their "normal" pain as fixable.
- **Scratch refactoring:** paste the code into a plain text file, rename and move things freely, knowing you'll throw it away. Gains insight and finds danger zones fast. Clausen: when your eyes glaze over trying to understand something, do mechanical work instead (e.g. break up long methods) since you can't solve problems while cognitively exhausted.
- **Changing practice in an org:** lead quietly by doing your work visibly well; curious people gravitate. As a consultant, convert people who are curious *and* listened to. Preaching creates enemies; you won't get 100%.
- **AI (March 2023 view):** code is still the representation language, so you must understand it to judge AI output. AI is "generate and test": the burden of verifying correctness is on you. Prompting becomes another (more frustrating) form of programming. Useful for generating test cases and ideation, and fuzz-like generated inputs. Coarse-grained modularity matters more: decide which stable pieces can be generated and which need human attention. Cohesion and coupling won't go away.
- **Discipline note:** starting on unforgiving tools (C, Notepad) builds a habit of complete attention you can dip into later.

**For Sam:** with AI writing much of the code, the codebase becomes "legacy" quickly (code you didn't write and don't fully understand). Counter it: type hints + pyright as the "compiler", behaviour tests at module boundaries as tripwires, and injected dependencies (pass the HTTP client/DB connection/config in, don't read globals inside functions). Use `git log --format= --name-only | sort | uniq -c | sort -rn` to find hotspots in his scripts and only harden those. Scratch-refactor an unfamiliar AI-generated script in a throwaway copy to learn it.

## Hynek Schlawack — Design Pressure: The Invisible Hand That Shapes Your Code (EuroPython 2025) (https://www.youtube.com/watch?v=msKPhXNi-A8)
**The shape of your data shapes your code; don't let the API schema or the DB schema (or a compromise between them) dictate the shape of your business logic. Map explicitly between layers and keep the domain model pure.**

- **Design pressure:** forces (tools, tests, input formats, laziness) that push your design one way, often unconsciously. Goal: make these trade-offs deliberately, not as "fate". ORMs and class-based validators (Django ORM, SQLAlchemy, Pydantic, Marshmallow) are fine tools; the danger is *unreflected* use.
- **Business logic is the reason the app exists:** the code that decides what to do from incoming data (web, DB, file, CLI). It usually ends up as scattered `if`s buried in views, form validation and DB access, because framework tutorials never show it separately. It can harm people (Therac-25 race condition overdosing patients; UK Post Office Horizon scandal: ~900 sub-postmasters prosecuted, 236 jailed). So you have a moral and practical duty to make it as correct and clear as possible.
- **Testing is a good design pressure** (via J.B. Rainsberger, "Integrated tests are a scam"): widening the scope of the system under test (whole service, end to end) masks the pain of coupled design. Coupling = two pieces can only be used/understood by looking at both; change one, change the other. Testing small units without monkey-patching half the universe pushes you to decouple. Watch for "test damage" (prod complexity existing only for tests), but overall listen to the pain. Brandon Rhodes: monkey-patching is software bankruptcy. (Note the tension with Ian Cooper's "test at the module API"; both agree on not mocking internals and on decoupling. Hynek's point is that the *domain* core should be IO-free and directly testable.)
- **"Structure your data so the problem solves itself"** (Matt Drury, "The rising sea", Advent of Code harbor/crane problem): clean domain classes (Instruction, Harbor, Stack; contents of boxes irrelevant), almost no conditionals. All the ugly parsing ("the darkness", six for-loops) lives at the edge. The core is elegant *because* it knows nothing of the input format. Lesson: validate **and reshape** data at the edges into the shape your problem needs; the input format may change, the domain logic shouldn't have to.
- **Three different "models" with conflicting goals:**
  - External/API model: shaped by what users want to send and API conventions.
  - Data model (DB schema): shaped by normalisation, performance, redundancy, sometimes by a separate DBA team.
  - Domain model: shaped only by the problem. Both API and DB models are hard to change in practice (consumers depend on APIs; migrations are painful under load, and greenfield is rare), so they *calcify*.
  - Bad: pick the API or DB model as your primary model ("database-driven design" is a pejorative). Worst: one unified class serving API + DB, a compromise forced onto the domain model as a double impedance mismatch.
  - Fix (quoting Adam Montgomery's "How I build" idea): duplicate-looking types per layer are OK; explicitly map between them rather than making a "franken-type" that lets the least flexible layer calcify the rest. Three or more classes for the same entity is fine.
- **State-specific types over one blob:** an invoice that is open (care: due date), paid (paid date), overdue (days overdue, reminders sent, plus enrichment from other sources/APIs) should be different types. Classes full of `X | None` fields are one of the biggest design smells. A little duplication beats the wrong abstraction (Sandi Metz); share via composition or specialisation subclassing if needed. Ask "what do I want to do and what do I need for that?", not "what attributes could this entity have?".
- **Example: postal addresses.** A data model with every field optional (some countries need only a postcode, some have none) is useless for logic; you drown in `if x is None` or fight the type checker. Define explicit shapes (e.g. `USAddress` with required fields, only `addr2` optional) that type checkers (mypy, ty) can verify. The boundary can be as small as one mapping function call.
- **Practical recommendations:**
  - Start from the domain model; then design the best user interface; then the optimal storage shape; accept the conflict and map.
  - Repository pattern: use the ORM's convenience to build queries, return plain dataclasses with encoded state, precise types, few optionals, no IO, easy to test.
  - On the API side, use Pydantic discriminated (tagged) unions to receive narrowed, tightly typed classes.
  - Make illegal states unrepresentable; static typing is itself a design pressure. Django `.values('col')` strings can't be typed; over-fetching is real (a friend's team hit Postgres's 1,664-column limit via careless joins).
  - It depends: a pure pass-through lookup service (request -> query -> JSON, plus authz) doesn't need a domain model; a dict is the right shape there. Don't go to raw SQL + dataclasses everywhere.
  - Weigh mapping cost vs. running algorithms on bad structures: 4 dict lookups + a full list scan per loop iteration is both ugly and slow.
- **Laziness masquerading as simplicity.** Shortcuts to avoid writing a second representation cost you later: every `if` doubles code paths (exponential), business code coupled to caches, inability to refactor toward new understanding. Proper design is delayed gratification. Easy (familiar, nearby, fewer keystrokes) is not simple (not interleaved/coupled), per Rich Hickey's "Simple Made Easy". Raw dicts instead of classes, god classes, DRY taken to extremes: easy, not simple. Interrogate people who throw around KISS/YAGNI/DRY: are they pursuing simplicity or being lazy? "Easy to parrot pearls, hard to have earned opinions." AI can press the keys now, so saving keystrokes is no argument.

**For Sam:** directly applicable to supplier integrations: Viator/RateHawk/Coras each have their own external schema; write one adapter per supplier that parses into *Trameter's* domain types (e.g. `Offer`, `BookingRequest`, `ConfirmedBooking`, `CancelledBooking` as separate state types) and never let a supplier's JSON shape leak into booking logic. Same for location data: GeoNames/OSM rows are a data model; map to a typed internal `Place`. In DataFrame-heavy pipelines, the equivalent is a single "normalise" step at ingestion that fixes column names, dtypes and nullability so downstream code can trust them.

## Kent Beck — Tidy First? A Daily Exercise in Empirical Design (GOTO 2024) (https://www.youtube.com/watch?v=Saaz6D1azlU)
**We design so we can change software cheaply; the cost of change is dominated by rare, huge changes caused by coupling, so invest in structure continuously, in small interruptible steps, balanced against economics (survival, NPV, options) and human relationships.**

- **Origin:** Beck set out to update Constantine & Yourdon's *Structured Design* (1970s), whose core claim is the "Newton's laws" of software cost: coupling is the central design issue. Original definition worth reviving: **two elements are coupled with respect to a particular change if changing one forces changing the other.** Not "service A calls service B" (that's runtime dependency, a different topic).
  - Coupling is change-specific: callers are coupled to a function's *name* but not to its internal formatting.
  - Tooling changes coupling: an IDE rename that updates all callers in one step removes the propagation. External/published API callers make it much more expensive (you can't change them in one go).
- **"Tidy first?" moment:** you need to change messy code; do you tidy it first? The smallest quantum of design, faced ~20 times a day. Answer: sometimes yes, sometimes no; usually yes, but don't get carried away. Tidying first is self-care for the programmer (e.g. extract a few helpers, then make the change).
- **Two layers of development:** visible behaviour changes (features, also operational/resource behaviour) and invisible structure. Structure strongly affects feature cost; it is never perfect; only the programmer on that path sees it, so it is chronically underinvested (technical debt shows up only later as slower features and more defects, too late). Goal of "empirical software design": balance investment in features and structure.
  - Feedback both ways: features reveal better structure; better structure suggests features. **Gusto story:** two separate US payroll calculators (8,700 tax authorities) were duplicated for valid reasons; once the pain was high enough they unified them, which made it cheap to embed a payroll calculator on the marketing homepage, a popular feature nobody would have built when it was expensive. Structure creates non-linear "jackpot" opportunities, but only if people know something became cheap.
- **Cost structure (Constantine's equivalence):** cost of software ≈ cost of changing it ≈ cost of the *big* changes. Changes follow a power-law: most are easy, a few cascade (change 1 part -> 4 -> 75 -> 4,000), like avalanches when the branching exponent is slightly above 1. From outside it looks random ("one week, one week, six months?"). Every coupling decision is a trade-off between the cost of coupling and the cost of decoupling.
- **Three constraints on any design style:**
  1. *Social:* build/maintain/repair trust; align authority and responsibility. If your API redesign creates work for others, help do it (or don't create it), and make sure they learn the new thinking. Incentives diverge (product wants features, engineering wants structure); you need agreement on the next step, not identical views. The social fabric changes (juniors grow, people leave), and documentation doesn't solve that: it's stale when needed, and keeping it current snowballs until abandoned. Communicate through code.
  2. *Medium:* the nature of software cost above.
  3. *Economic:* (a) **survival**: software defaults to failure until it crosses sustainability (explore -> expand -> sustain phases, via Peters' *Ergodicity*); design must improve odds of surviving early. (b) **Net present value**: earning sooner = earning more; spending later = spending less. Deferring a design decision creates value; why big design up-front loses. (c) **Optionality**: structure creates options to change in more directions; options are worth *more* the less predictable the environment.
- **Implications he draws:**
  - **Grow like a tree** (Dave Farley): design is mostly differentiation, start tiny and split parts as they grow; occasionally unify duplicates.
  - **Design is an activity, not a phase.** Avoid the "feature hamster wheel" and also "stop for six months to fix it" (relationship killer; best case the software does the same thing six months later). Interleave features and design; do as much design up front as you like, but only a bit, because you'll get to design again.
  - **Key skill: parallels.** Keep old and new designs coexisting so design work is interruptible and always deployable. Micro example for changing a parameter's type: add a new parameter (deploy), switch uses to it (deploy), delete the old one (deploy). Works at all scales (expand/contract).
  - **Strict separation at micro level:** never mix structure changes and behaviour changes in the same change/commit; if you catch yourself doing both, start over and split them. At macro level they interleave freely.
  - **Lead with purpose, not pressure:** design is creative and needs both impetus and space; "work a couple extra hours" never yields improving structure.
- Waste-aversion as the motivating value (~3 billion seconds in a life): XP = strip development to what demonstrably matters.

**For Sam:** as a solo builder, "tidy first" is a 5-minute habit: before asking AI to add a feature to a messy script, first make (or ask for) a pure tidy commit (rename, extract function, reorder) with no behaviour change, verify outputs unchanged, then a separate feature commit. Use parallels for schema/column or supplier-API changes: add the new field/path alongside the old, migrate callers, then delete. NPV argues for deferring heavy architecture on Tereka/Trameter features until real usage appears; optionality argues for keeping supplier code behind one internal interface so new suppliers are cheap.

## Jack Diederich — Stop Writing Classes (PyCon 2012) (https://www.youtube.com/watch?v=o9pEzgHorH0)
**A class with two methods, one of which is `__init__`, is a function; prefer functions, built-in data structures, flat namespaces and standard exceptions, and delete code relentlessly.**

- **First principle:** you ship features, not code; code is a liability. Every line must be read (including third-party code you vendor: you read it before adopting and diff every update). His four-person team *reduced* product line count over a year while shipping features. Zen of Python: simple > complex, flat > nested, "if it's hard to explain it's a bad idea".
- **The #1 smell:** a noun-named class whose `__init__` stores args and which has one other method; callers instantiate it, call the method once, discard it (or alias it to a short name). That is a function. 10 lines -> 2. If you always pass the same first argument, use `functools.partial` instead of a class.
  - Counterpoint raised in Q&A: a partial/closure hides its bound state from introspection; for public library APIs a small class can expose it. Fine for libraries, but default to functions in application code.
- **"Might need it later" is the root cause** (ex-Java habits, CS curricula, premature generalisation). Example `MuffinHash(dict): pass` in its own module, referenced everywhere; every reader must go check it's empty. Google API client's empty `Flow` base class and an aliased stdlib exception have the same cost. If you write `class X: pass`, look into your soul. If you added it for a reason that never materialised, refactor it out.
- **Case study, "MuffinMail" API client:** v1: 1 package, 22 modules, 20 classes, ~130 methods, 660 lines, to send emails to a list and get back bounces/unsubscribes. v2 (new developer): 15 lines using only stdlib, plus a 20-line test suite, but still a two-method class whose second method was `__call__`. v3: a ~5-line function at the top of the calling module: zero modules, zero classes. Easier to read, use, and diff.
- **Namespaces prevent collisions; they are not taxonomies.** Deep hierarchies (`muffinmail.muffinhash.MuffinHash`, `services.crawler.crawlexceptions.ArticleNotFoundException`) make people remember and type more. The stdlib: ~200k lines, ~200 top-level modules, very flat.
- **Exceptions:** stdlib defines only ~165 exceptions in 200k lines. Prefer built-ins (`LookupError`, `KeyError`, `ValueError`). Don't put "Exception"/"Error" redundancy in names; `raise`/`except` already says it's an exception. Define custom ones only when a caller needs to catch that specific condition. Q&A nuance: catching a broad built-in like `KeyError` may swallow unrelated errors; subclassing a built-in (`class MissingFare(KeyError)`) keeps compatibility while making it specifically catchable. Agreed approach: create them when you need them, not before.
- **When classes are right:** a bundle of mutable state plus several functions operating on it. Example: `heapq` functions all take the same heap as first argument, which signals a class; he keeps a small `Heap` class with a `key` scoring function (useful for A* pathfinding: score on push, discard on pop). Also OK: a class as a tiny namespace for a few constants/functions when a module would be overkill.
- **Game of Life:** naive OO design has `Cell` (position, alive, next state, neighbours) and `Board`. Notice Board is a two-method class wrapping a dict -> use a dict; position is the key -> drop it; alive is membership -> use a **set** of live coordinates; next state -> build a new set each generation. Result: a neighbours generator plus a short step function, the whole game in a handful of lines.
- **OAuth example:** 10k-line Google client and a 540-line library didn't fit; he wrote a 135-line bearer-token client (and admits one class was still an unnecessary `class Error(Exception): pass`).
- (note: his dismissal of "separation of concerns / encapsulation" as words people use to "pull a fast one" is a rhetorical jab; the concepts matter, as other talks here show. His real point is to avoid speculative structure.)

**For Sam:** AI assistants love generating Java-style scaffolding: `SupplierClient` classes with one method, `BaseProcessor` hierarchies, a custom exception per file, `utils/helpers/core` package trees. Push back: for a data step, a module of plain functions over DataFrames/iterables is usually best; a supplier client earns a class only when it holds real state (session, auth token refresh, rate-limit counters) used by several methods. Keep package trees flat. A set of tuples or dict keyed by ID often replaces a whole object model in matching/dedupe code (and is faster).

## Dan Abramov — The WET Codebase (https://www.youtube.com/watch?v=17KCHwOwgms)
**Duplication is cheaper than the wrong abstraction; when an abstraction starts sprouting special cases, inline it, test concrete features rather than abstractions, and keep your code easy to un-abstract.**

- **The story of an abstraction (how good intentions build a monster):**
  1. Two modules contain similar code; reviewer cites DRY; it's extracted into a shared module. Fine so far.
  2. A third case needs "the same but synchronous"; rather than copy, the abstraction is generalised to handle both.
  3. The new case turns out to need something slightly different (a bug): add a special-case `if`.
  4. The original case was also subtly different: another special case.
  5. Abstraction looks scary, so it's made "generic": special cases pulled out into parameters supplied by every call site. Nobody now understands what it represents.
  6. Team churn; people make small local fixes without the big picture; you get cyclic dependencies and odd growths. Nobody wants to touch it; eventually someone rewrites it.
  Each step looked reasonable to author and reviewer; the problem is only visible in aggregate.
- **The fix (with a time machine):** at step 2-3, **inline the abstraction**: copy the code back into each call site. Now each copy can diverge to fix its own bug without affecting others. Later, if pieces genuinely stabilise, extract something, likely a *different* abstraction than the first guess. "As good as it gets in practice."
- **Why best practices go wrong:** a self-perpetuating loop: one generation learns from concrete problems, compresses lessons into "best practice / anti-pattern" without the context, the next generation applies them to extremes and creates new problems. Break it by teaching the trade-off (what you gain, what you give up, and the "expiration date" of the context that justified it). Challenge: deconstruct a practice you strongly believe in.
- **Benefits of abstraction (real):** focus on one intent/layer (`send_email()` without knowing SMTP); reuse; avoid the bug where you fix one copy and forget the other.
- **Costs of abstraction:**
  - *Accidental coupling:* a fix for one caller lands in shared code, so you must reason about every other call site.
  - *Extra indirection:* the promise of focusing on one layer breaks when a bug spans layers; your mental stack overflows. Avoiding spaghetti code produces "lasagna code" (too many layers).
  - *Inertia (social):* newcomers can't unwind what they don't understand and don't want to be the one proposing copy-paste. It may become literally impossible: other teams depend on it, a reorg leaves no owner, nobody knows how to test it. "Easy-to-replace systems tend to get replaced with hard-to-replace systems" (a Peter principle for code).
- **Mitigations:**
  - **Test code with concrete business value**, not the abstraction. Tests on the abstraction break the moment you inline it, so you revert (nobody wants to delete tests or lower coverage). Tests on concrete features don't care how many layers exist and actually guide the refactor. (Same principle as Ian Cooper's "test behaviour, not implementation".)
  - **Restrain yourself:** structurally similar snippets may be accidentally similar; wait until the problem proves to be the same one (his analogy: liking the same obscure bands doesn't make two people life partners).
  - **Culture of deleting abstractions:** it should be normal to say in review "this is out of control, let's copy-paste it back and figure it out later".
  - **Technical shape matters:** inlining is hard with tangled dependency graphs and shared mutable state (would have to duplicate and rewire state). Tree-shaped dependencies with one-way data flow (React components: Button used by Form used by App) make inlining a copy-paste, so mistakes are reversible before it's too late.
- Further reading he recommends: Sandi Metz "All the Little Things", Sebastian Markbåge "Minimal API Surface Area", Cheng Lou "On the Spectrum of Abstraction".

**For Sam:** a frequent trap with multiple suppliers or data sources: a shared `normalize_provider_response(provider, ...)` that accumulates `if provider == 'viator'` branches. Prefer one straightforward adapter per supplier (duplication allowed) mapping into a shared *output type*; share only small, truly identical helpers once they've stabilised (rule of three). When an AI suggests "let's make this generic", ask what the concrete second and third cases really need. Keep pipeline tests at the level of "this input file -> these output rows" so refactors toward or away from abstraction stay safe.
