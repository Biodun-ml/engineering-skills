# ai-2 — cross-cutting principles

1. **Look at your data first, before any metric, judge or framework.** Read 20–30 real outputs in a friction-free viewer, write free-form notes, cluster them into failure modes, count them, and fix the most frequent first. Stop when 5–10 more examples show nothing new. (Hamel & Shreya — Error Analysis; Hamel & Dan — Instrumenting & Evaluating LLMs; Chip Huyen — Pragmatic Engineer)
2. **Build a custom annotation/trace viewer that shows outputs as they really appear** (email as email, article with highlighted extractions), with hotkeys and a running list of notes. An AI coding assistant builds one in minutes. Buy trace logging; build the viewer. (Hamel & Shreya; Hamel — Instrumenting)
3. **Tier your evals: code assertions → aligned LLM judge → humans.** Assertions catch the "dumb" failures, can run in production for retries, and are logged per feature × scenario. Use them as hard gates (safety) or as a leaderboard (quality). (Hamel & Dan — Instrumenting)
4. **An LLM judge is a model you must evaluate.** Align it to an expert's labelled critiques (Hamel reached ~94% agreement), swap positions to catch order bias, re-check agreement regularly, and pin and version the judge's model and prompt. A score from someone else's off-the-shelf judge prompt can't be interpreted. (Hamel & Dan; Chip Huyen — MAD; Bryan Bischof)
5. **Criteria drift, for humans too.** Raters' standards rise as outputs improve, and graders redefine "good" while reading. Compare variants inside the same time window (A/B), keep grading continuously, and treat eval criteria as living. (Dan Becker — alt-text; Shreya Shankar — EvalGen; Kapoor — "who validates the validators")
6. **Evaluate each pipeline stage separately so you can find where it fails.** A resume pipeline that was wrong 50% of the time couldn't be fixed because nobody knew which stage failed. Score retrieval as retrieval, extraction as precision/recall, agent planning as per-step classification, and the final summary on its own. (Chip Huyen — Pragmatic; Bryan Bischof; Eugene Yan)
7. **Build what you can evaluate, and measure what users actually care about.** Adoption follows evaluability (code, recommenders, fraud). Work backward from the business metric. Users wanted their own action items, not "accurate summaries", and suggested questions, not better answers. Generic metrics (helpfulness, conciseness) are mostly noise. (Chip Huyen — both; Hamel & Shreya)
8. **Keep a hard eval suite.** Aim for roughly 60–70% pass rates, delete evals that never flip, replay historical production traffic through new variants, and test for significance. A 100%-passing suite gives no signal. (Bryan Bischof — Instrumenting)
9. **Retrieval is old IR: measure it on your own judged set against BM25.** A TSV of (query, doc, label), recall@k / precision@k / nDCG / MRR, LLM relevance judges validated on ~100 gold pairs, hybrid keyword+dense search, chunks of ≤ ~256 tokens per vector, and the ability to return *zero* results. kNN always returns something, so threshold scores or blind rank fusion will blend in junk. (Jo Bergum; Chip Huyen; Eugene Yan)
10. **Climb the complexity ladder only as far as needed:** prompt → examples → retrieval/data preparation (contextual chunk metadata) → fine-tuning last. Fine-tunes carry hosting and maintenance costs and are quickly overtaken by new open models. Mind the "fitting ≠ using" limit of long context. (Chip Huyen — both)
11. **Prefer workflows to agents when the decision tree is mappable, volume is high, budgets are small, or errors are costly and hard to detect.** If you do build an agent, keep it to environment + tools + system prompt, and debug from inside its context window. (Barry Zhang — Effective Agents)
12. **Compile recurring agent behaviour into deterministic structure.** Hard rules go in code, a calibrated model handles scored decisions, the LLM handles only the fuzzy parts, and you add human escalation plus a lint loop. Repeated code becomes a saved script. This brought one task from ~7.5 to ~2 minutes and let it run on a small model. (Blumenfeld — Graph Engineering; Zhang & Murag — Skills)
13. **Reliability, not capability, is the AI engineer's job.** pass@k ≠ right every time, and 80% right is a product failure. Verifiers have false positives, so retry-until-pass can bend accuracy downward. Watch for reward hacking: sanity-check results against physical limits. (Kapoor)
14. **Always report cost (and latency) next to accuracy and choose from the Pareto frontier.** A model with similar accuracy at 10× lower cost wins. Jevons paradox means total spend grows as unit prices fall. Budget roughly $0.10/task ≈ 30–50k tokens. (Kapoor; Zhang)
15. **Use the cheapest component that works and route between them.** Production GenAI systems are hybrids: an intent/router classifier sends easy items to cheap or local models, hard ones to strong models, and sensitive ones to humans, with PII/toxicity classifiers on outputs. Small fine-tuned evaluators (Eugene's NLI hallucination detector, ~20 ms/query, bootstrapped with adjacent public data) can replace LLM calls at scale. Token logprobs give a cheap confidence signal. (Chip Huyen; Eugene Yan)
16. **Treat all third-party content as untrusted input.** Prompt injection via hidden text in web pages, images and docs, exfiltration via rendered URLs, jailbreaks via role-play or encodings, and data poisoning are all live risks. Never let retrieved content drive tool calls or URLs, and validate model-produced IDs and facts against your own data, because models "dream" plausible-looking IDs. (Karpathy)
17. **Carry provenance end to end.** Attribution to source passages, audit trails, and automated claim-checking are how you manage the inevitable 5–10% inaccuracy. Persist each run's path through the pipeline to find failing or dead branches. (Douwe Kiela; Blumenfeld)
18. **Ship to real users early and hill-climb. Design for production from day one, not for the pilot.** Integrate into existing workflows, and use crawl-walk-run rollout: AI suggests, humans accept, then automate the categories with high acceptance rates. (Douwe Kiela; Chip Huyen — Microsoft crawl-walk-run)
19. **Package expertise as versioned skills plus MCP.** A general agent (loop + bash + file system) with MCP for connectivity and progressively disclosed skills (folders with instructions, scripts and assets) for expertise beats a bespoke agent per domain. Test that skills trigger correctly, and version them like software. (Zhang & Murag — Skills)
20. **Own and version your prompts as engineering artefacts.** Make prompt changes as tracked experiments. Framework default prompts can change silently between versions. Your prompt edit history shows where the model fails: repeated "do not X" edits are ready-made assertion candidates. (Chip Huyen; Shreya Shankar — SPADE)

## Hamel Husain & Dan Becker (+ Harrison Chase, Bryan Bischof, Eugene Yan, Shreya Shankar) — Instrumenting & Evaluating LLMs (https://www.youtube.com/watch?v=SnbGD677_u0)
**Evals plus looking at data are the engine of iteration speed: cheap code assertions first, aligned LLM judges second, humans as the trusted standard, all logged so you can see progress.**

- **Mental model.** Improving an LLM product (prompting, RAG, fine-tuning) is an iteration loop; how fast you get trustworthy feedback decides how fast you improve. Evals and data inspection are "the applied part" of applied AI. Three eval tiers: (1) unit tests / assertions (code, fast, cheap), (2) LLM-as-judge, (3) human review. Choose the mix per use case.
- **Two ways to use assertions.** (a) Hard gates: must all pass, otherwise block (good for safety items like leaking an internal user ID from the system prompt into output). (b) Leaderboard style: you don't expect 100% pass, you track pass rate going up across prompt/model/fine-tune variants. Internal tools where a human edits the output anyway (Dan's text-debiasing for a publisher) tolerate more failure than public-facing products.
- **Finding assertions.** Hamel claims every real project has "dumb" failure modes testable with code; you find them only by looking at traces. Write tests by enumerating **features × scenarios** (ReChat: "find listings" feature → scenarios: one match, many matches, zero matches) and generating test inputs per scenario, synthetically with an LLM if you lack user data. Make assertion logic reusable so it also runs in the production path (self-healing / retry), and **log results to a database** (they used existing Metabase) to chart failure rate per feature/scenario per iteration.
- **LLM-as-judge must be aligned.** Have a domain expert label outputs good/bad *with a written critique* in a spreadsheet; iterate the judge prompt until agreement with the human is high (Hamel reached ~94% on Honeycomb query generation over a few weeks). Use the strongest model you can afford for the judge; re-check agreement periodically (it is not one-off). Dan's counter-example: in pairwise comparison the judge said "A better than B" and also "B better than A" when order swapped — no transitivity, so he dropped the judge. Always test position bias by swapping order.
- **Human eval gotcha: rater drift.** Alt-text project: human scores showed model 4 as best, later models apparently worse. In fact raters' standards rose as they saw better outputs (0.65 became 0.5). Fix: randomised A/B within the same time window so drift cancels out. Fine when you have labellers and volume; impractical early.
- **Traces.** A trace is the logged sequence of events for one interaction (turns, retrieval, tool calls), often stored as JSONL — the most valuable asset for debugging and later fine-tuning. **Remove all friction from viewing data**: Hamel built a domain-specific trace viewer in under a day (Shiny for Python; Streamlit/Gradio also fine) showing tool, scenario, synthetic vs real, review counts. Buy trace logging (LangSmith, Braintrust, W&B Weave, Logfire, OpenTelemetry, Inspect) rather than build it; spend your effort looking.
- **LangSmith workflow worth copying regardless of tool:** filter traces by error, latency, model tag, user feedback; push bad production traces into a dataset ("traces → dataset" so failures never recur); split datasets by failure mode and test splits separately; compare experiments side by side on the cases that flipped; annotation queues for humans; judge correction loop where human corrections become few-shot examples for the judge.
- **Bryan Bischof (Hex Magic) — opinionated rules.**
  - Evals exist to (1) decide a capability is good enough to ship, (2) let you sleep (detect bad behaviour), (3) help debug later.
  - LLM eval is not a new field; turn fuzzy outputs into old-school measurable checks. Code gen → *execution evaluation* (run generated SQL/Python, compare resulting dataframes with "relaxations": same data even if shape/column order differ). Agent planning → binary classification per step (required vs flexible steps). Summaries → does it contain the key points.
  - Involve domain experts to define "good" (chart generation: check chart type, x axis is datetime, y aggregated — binary checks, not pixel match).
  - Evals are written in the RFC, before building.
  - Product metrics ≠ eval metrics; production logs tell you what to build evals for, not the evals themselves.
  - You don't need an eval framework until you feel pain; his was one class over unit tests and a Jupyter notebook.
  - LLM judge gives directional signal; use it after you have real evals, with side-by-side comparisons, multiple judges/shots, random human spot checks.
  - **RAG: evaluate retrieval as retrieval** — label best docs per query, measure hit rate, have a baseline before tuning chunking/hybrid. Retrieval scores are not calibrated confidence.
  - Evaluate the agent's final summary step too (it can describe things the agent never did); don't feed it the whole chain's context.
  - Changes to a pipeline are repeated-measures experiments: replay historical production events through the new variant and test significance.
  - Don't clone production inside the eval harness; call production endpoints, with each step exposed so you can inject mid-pipeline.
  - **Target 60–70% pass rate**; a 100%-passing suite has no signal. Delete evals that never flip. Bootstrap-sample to get early signal on long suites.
- **Eugene Yan — cheap evaluator models.** Hallucination in summaries ~5–10% by human review. Frame factual inconsistency as NLI: P(contradiction) between source and summary. Fine-tuned a small NLI-pretrained encoder with LoRA (<3% params trainable). On the target benchmark (FIB, ~700 balanced training pairs) alone: ROC-AUC 0.56→~0.65, recall@0.8 stuck below 10% — unusable. Pre-training first on a larger related dataset (USB, ~5k pairs), then the target: ROC-AUC 0.75→0.86, recall 0.57, precision 0.93. Lesson: **blend in permissively licensed adjacent data** to bootstrap a small classifier. Runs ~20ms/query, usable both as offline eval and as a production guardrail. Split by source document to avoid leakage; track PR-AUC/ROC-AUC/recall/precision at a chosen threshold; plot the score distributions of positives vs negatives.
- **Evaluating agents = evaluating a multi-step workflow.** Split prompts into steps (extract decisions/owners → precision/recall; check extraction against transcript → consistency classifier; rewrite as bullets → softer style metric).
- **Shreya Shankar — evals as scaled human judgment.** LLMs ignore instructions some % of the time at scale, so you need assertions. Criteria are task-specific and hide in your **prompt edit history** (repeated "do not include X" edits flag where the model fails; inclusion/exclusion rules are the most common). Use an LLM with a taxonomy of edit types to propose 3–5 candidate assertions, not 15. **Criteria drift**: graders change their own definition of good after seeing outputs, so grading must be continual (her startup posts daily outputs to a Slack channel). People want code for crisp checks (format) and LLM judges for fuzzy criteria or dirty/typo'd data; they want per-criterion thumbs up/down.
- **RAG retrieval metrics (Eugene):** recall@k, ranking (NDCG), and the often-missed one: **can retrieval return zero results** for queries with no relevant docs? Pure kNN always returns something; threshold on similarity/BM25 score and answer "I don't know" deterministically. Dan used a low-relevance threshold as a cheap adversarial-user detector (the DPD chatbot haiku incident). Remove toxic/false docs from the index rather than hoping the generator ignores them.
- **Practical:** temperature 0 for classification/extraction (deterministic), higher for creative; run quality evals locally for fast decisions, put safety assertions in CI. Don't fine-tune the judge ("turtles all the way down"). Start without formal evals, poke at the model, then add tests as failures appear (~30 samples is enough to start).
- **For Sam:** for the blog→trip pipeline, define features × scenarios (article has 0 / 1 / many bookable places; non-travel article; listicle vs narrative) and generate synthetic articles per cell. Hard-gate assertions: output JSON parses, every extracted place appears in the source text (watch typo-correction), place IDs exist in the master location table. Align the LLM gate's judge against Sam's own labels. For million-row location classification, Eugene's recipe applies directly: label a few hundred rows, fine-tune a small classifier (or use one as a filter) instead of calling an LLM per row; track precision/recall at the decision threshold.

## Chip Huyen (with Gergely Orosz) — AI Engineering with Chip Huyen (https://www.youtube.com/watch?v=98o_L3jlixw)
**AI engineering flips ML's order (product → data → model): start from an API call and a clear definition of a good response, climb a complexity ladder only as far as needed, and invest in evaluation and data, not shiny tools.**

- **What changed vs ML engineering.** Before: collect data → train → deploy inside an existing product. Now: demo first via API, then gather data (mainly for eval and prompt examples), and only later host/fine-tune a model when cost or quality forces it. Advantage shifts to product understanding and proprietary data, since everyone has the same base models. Real GenAI systems still contain lots of classical ML: an **intent router** (cheap model for easy queries, expensive model for hard ones, human for sensitive ones like billing disputes), PII/toxicity classifiers on output, and retrieval systems.
- **How she separates durable vs temporary knowledge.** For each problem/solution, ask: is this a fundamental limitation of AI or a temporary capability gap, and how fast is that gap closing? Prompt hacks (bribing the model, fragile phrasing) faded as models became robust to prompt perturbation; context length went 8k → 128k quickly, so the durable question is **context efficiency** (does the model actually use the context well), not length.
- **Development ladder (in order):**
  1. Define what a good vs bad response is. Not obvious: LinkedIn's job-fit assessment initially optimised correctness, but "you're a terrible fit" is useless; users wanted the gaps and how to close them. Turn that into explicit guidelines in the prompt.
  2. Prompt, look at outputs, add examples; build a query set with expected responses; measure with automated metrics, LLM judge, and human eval.
  3. Add context (RAG). Don't jump to vector DBs: embeddings depend on embedding quality, cost money/latency, and blur exact tokens (error codes, IDs). Start with keyword retrieval; benchmark anything against **BM25** (a practitioner's rule: ignore any retrieval system not compared with BM25); go hybrid (term + semantic) when needed.
  4. Data preparation gives the biggest RAG gains: chunking for context fit, but chunks lose referents (doc says "company X", later chunks say "the company") → add metadata, titles, summaries, or Anthropic-style **contextual retrieval** (LLM-generated context prepended to each chunk).
  5. Fine-tuning last. It brings hosting, memory, maintenance, and obsolescence risk: a newly released open model may beat your fine-tune within weeks. Organisations usually get more return from enabling new use cases than squeezing a few points on existing ones.
- **Rollout pattern (Microsoft "crawl-walk-run").** Customer support: first AI drafts suggestions that humans pick/edit; measure acceptance rate per query category; when a category hits ~90% acceptance, automate it for a small/internal audience, then expand. Before GenAI, check the real bottleneck: one startup solved support load by moving questions to a public Discord; others just needed a ticket **triage classifier**.
- **Why evaluation is hard.** The smarter the model, the harder to judge (a convincing book summary requires reading the book). Three methodologies: **functional correctness** (does the code run and produce expected output; does the AI actually save energy — why coding is the most mature use case), **AI-as-judge** (widely adopted, but depends on judge model + prompt and is non-deterministic, so it drifts), and **comparative evaluation** (humans can say which of two is better even when they can't score absolutely).
- **Measure what users care about.** Meeting summariser team agonised over 3 vs 5 sentences; users only wanted *their own action items*. A tax-software chatbot failed because users hate typing and didn't know what to ask in an unfamiliar domain — fix was suggested questions, not better answers. Eval tooling can't replace talking to users and reading interactions.
- **Human eval habit.** Daily, look at ~50 real interactions with a clear rubric (more if resources allow). It shows usage shifts (current events), and gives a baseline to detect when LLM-judge scores diverge from human scores.
- **Common mistakes.**
  - Using GenAI where a simple rule wins (energy-scheduling startup vs "run heavy appliances off-peak").
  - Giving up on GenAI after a bad attempt that was really bad prompting/product/eval.
  - **Not localising failures**: a resume pipeline (PDF → text → organisation extraction) was wrong ~50% of the time and the team couldn't say which stage failed. Evaluate each stage separately.
  - Premature complexity: vector DBs, fine-tuning, agent frameworks. Framework default prompts had typos that got silently fixed in later commits, changing app behaviour without you knowing — own your prompts and pin versions.
- **Learning and focus.** Mix project-based learning with structured learning; tutorials invite mindless cell-running (she found many repos importing a library they never used, copied from a tutorial). Ignore news unless it helps the problem you're on; important things are still important in two weeks. Exercise: log a week of your work and ask what share AI could do.
- **On software engineering's future.** Coding is the visible act; engineering is precise problem solving. AI writing code lets one engineer handle more complex systems, as printing let books grow longer.
- **For Sam:** the blog→trip pipeline is exactly the multi-stage case — log and score each stage (gate, extraction, matching, trip building) separately so failures are localised. For location classification at scale, put a router in front: rules/keyword/BM25 or a small classifier for easy rows, an LLM only for ambiguous ones. For matching extracted place names to GeoNames/OSM, start with keyword/BM25 plus metadata (country, admin region) before embeddings, because exact names and IDs matter.

## Chip Huyen (with Matt Turck) — What You MUST Know About AI Engineering (https://www.youtube.com/watch?v=p7F4f42iZ-c)
**Foundation models make building easy and evaluating hard; treat prompts, judges and context as versioned engineering artefacts, keep RAG, and see agent planning as a search problem whose difficulty depends heavily on tool design.**

(Overlaps with her Pragmatic Engineer interview; only new material below.)

- **Three-layer stack.** (1) Application development: prompt engineering, structured output enforcement, guardrails, evaluation. (2) Model development: fine-tuning, distillation, quantisation, inference optimisation — only after the app layer is maxed out. (3) Infrastructure: compute, storage, deployment, a platform for fast iteration. Hybrid systems remain the norm (intent classifier routing hard queries to a strong model, easy ones to a local open model, sensitive ones to a human; PII detector on output). "XGBoost isn't being replaced."
- **Why language scaled.** Language modelling is **self-supervised**: the next token is a free label, so any text or code is training data, unlike translation or fraud detection that need curated labels. Bigger models have more capacity; training a large model on little data wastes compute — larger models need more data to realise their capacity. "Small" is time-relative: newer small models (e.g. Llama 3 small) beat older big ones thanks to better data, training and alignment. Practical ways to get a performant small model: **quantisation** (works broadly), **distillation** (big model teaches small one); mixture-of-experts (shared parameters + router between expert sub-networks) is harder to train and not something app teams should start.
- **Pre- vs post-training.** Pre-training = next-token completion ("how to make pizza" → "for six"). Post-training = supervised fine-tuning on instruction→response demonstrations, then preference optimisation (RLHF, DPO) to raise good-response likelihood and lower bad. Because labs scrape similar web data, **post-training is where models differ** (Claude vs GPT vs Gemini).
- **Sampling is underrated.** The model outputs a distribution; sampling picks from it, token by token. Temperature trades predictability vs creativity (too low → boring/common phrasing; too high → incoherent). It's a cheap lever that needs no retraining. **Use token probabilities for debugging and confidence**: if the correct "yes" has low probability, the model is unsure — a signal to inspect (useful for classification pipelines: use logprobs of the label token as a confidence score).
- **Evaluation-driven development** (from test-driven development): build what you can evaluate. Adoption follows evaluability — recommenders (click/purchase rate), fraud (losses stopped), coding (compiles, passes tests) are popular because ROI is measurable. Work backward from the business metric (text-to-SQL: time to write a correct query drops from ~3 min to ~1 min) to offline model metrics you can check before deploy. Perplexity/entropy matter to model builders, rarely to app builders (note: entropy falls with longer preceding context; there is an irreducible floor).
- **LLM-as-judge caveats.** Correlates well with humans, widely used, including as a production check on a response before it's returned. But it is not an exact metric like F1: its value depends on judge model + prompt, and if either changes, 90% → 92% is not comparable. Anecdote: an engineer reported "faithfulness 90%" from an off-the-shelf judge without knowing its prompt. **Pin and version judge model and prompt; own the prompt.**
- **Prompt engineering is real engineering.** It's human-to-computer writing: anyone can do it, few do it well. Old tricks (bribes) are noise; the discipline is **versioning prompts, treating each change as an experiment, tracking results**, so downstream teams know why outputs changed. In-context learning (zero-shot vs few-shot examples in the prompt) is what lets one general model adapt to any task without retraining.
- **Defensive prompting & security.** Matters more as AI gets tools and can act. Hosted APIs ship provider guardrails; with self-hosted open models you own all safety. System prompt (developer's instructions, role, tone, refusals) vs user prompt (end user's input) — defensive instructions live in the system prompt, but don't rely on them alone.
- **RAG is here to stay.** Long context won't kill it, for two reasons: usage always expands to fill capacity (like RAM), and **fitting ≠ using** — in her own novel-writing tests, models confused timelines and characters beyond roughly 10k tokens. Some providers advise "below N tokens, stuff the context; above, use RAG"; test context efficiency on your own task.
- **Agents.** Classic definition (Russell & Norvig): anything that perceives an environment and acts on it. Defined by its environment (web, Gmail, IDE/terminal), its tools, and its planner (the LLM). Tool use (function calling) is fairly well understood; **planning is the hard part** — it's a search over action paths, including deciding no path exists, and needs predicting each action's outcome. Practical levers: make tools easy to understand — clear names, good docs, split complex tools into simpler ones. Human-written plans are poor training data because what's efficient for humans (avoid reading 1,000 sites) differs from what's efficient for AI.
- **For Sam:** for million-row location classification on a budget: quantised small local model + label-token logprobs as confidence, escalating only low-confidence rows to a bigger model (router pattern). Version every prompt and judge prompt in git with eval results. Test how much article text the extraction model actually uses well before deciding to stuff whole long blog posts vs chunk and retrieve.

## Andrej Karpathy — [1hr Talk] Intro to Large Language Models (https://www.youtube.com/watch?v=zjkBMFhNj_g)
**An LLM is a lossy compression of internet text into weights, turned into an assistant by fine-tuning, extended by tools and retrieval into an "LLM OS" — and it brings a new attack surface (jailbreaks, prompt injection, data poisoning).**

- **Two files.** An open-weights model is a parameters file plus a small run program. Llama 2 70B: 70B params × 2 bytes (fp16) = 140 GB; the forward pass is ~500 lines of dependency-free C. Inference is cheap enough for a laptop (a 7B model runs ~10× faster than 70B). The expense is in getting the weights. Useful sizing rule: **weights memory ≈ params × bytes per param** (fp16 = 2, 8-bit = 1, 4-bit ≈ 0.5) — so on a 16GB machine, ~7–8B models at 4–8-bit are the practical ceiling, plus room for KV cache.
- **Pre-training = compression.** Llama 2 70B: ~10 TB of web text, ~6,000 GPUs, ~12 days, ~$2M → 140 GB of weights (~100× lossy compression). Frontier models are 10×+ beyond this. Predicting the next token well forces the network to learn facts about the world (prediction and compression are mathematically linked).
- **Generation = dreaming the training distribution.** Sampling token by token produces plausible documents; form is right, content may be invented (a made-up ISBN that has the right shape). You can't tell memorised from hallucinated output from the text alone → you need external grounding/verification for any fact (IDs, prices, coordinates).
- **Inscrutable artefacts.** The architecture (Transformer) is fully known; what the billions of parameters do is not. Knowledge is oddly one-directional (**reversal curse**: knows Tom Cruise's mother is Mary Lee Pfeiffer, not who her son is). Treat models empirically: measure behaviour with good evals.
- **Assistant training.** Stage 2 fine-tuning keeps the same next-token objective but swaps the data: ~100k high-quality human-written Q&A conversations written to labelling instructions (helpful, truthful, harmless; docs can run to hundreds of pages). Pre-training = knowledge (quantity); fine-tuning = alignment/format (quality). Fine-tuning is cheap (≈ a day) so labs iterate it often: deploy, collect misbehaviours, have humans write the correct answer, add to data, retrain. Optional stage 3: **comparison labels** (easier to pick the best of several outputs than to write one) → RLHF. Labelling is increasingly human–machine collaboration (model drafts, humans pick/edit/oversee). Base models just continue documents; open releases ship base + chat variants so you can do your own fine-tuning.
- **Ecosystem.** Chatbot Arena ranks models by Elo from blind pairwise human votes. Closed models led; open-weights models trail but may be "good enough" for your application and can be fine-tuned/self-hosted.
- **Scaling laws.** Next-token accuracy is a smooth, predictable function of N (params) and D (training tokens), with no sign of topping out; downstream benchmarks improve with it. Hence the compute gold rush; algorithmic progress is a bonus.
- **Tool use is the main capability trend.** In his demo the model searches the web, uses a calculator for ratios (models are bad at mental arithmetic), writes matplotlib code to plot and fit a trend, and calls an image generator. Design principle: **don't make the model do in its head what a tool does reliably** (arithmetic, lookups, plotting, date math). Multimodality (see/generate images, speech in/out) is a second axis.
- **Future directions (as of late 2023).** System 2: trade time for accuracy (think longer → better answer). (note: this has since materialised as reasoning models.) Self-improvement à la AlphaGo needs a cheap automatic reward; it's feasible in narrow domains with checkable outcomes, not general language. Customisation: custom instructions + uploaded files with RAG, later fine-tuning — many specialised experts rather than one model.
- **LLM OS analogy.** The LLM is the kernel orchestrating resources: context window = RAM (finite, precious working memory; the kernel pages relevant info in/out), disk/internet = retrieval, tools = software, plus parallels to multithreading, speculative execution, user vs kernel space. Proprietary (GPT/Claude/Gemini) vs open (Llama-based) mirrors Windows/macOS vs Linux.
- **Security — cat-and-mouse:**
  - *Jailbreaks*: role-play ("my late grandmother used to tell me how to make napalm"), encoding (Base64 bypasses refusals trained mostly in English), optimised universal adversarial suffixes (re-optimisable after patching), adversarial noise in images.
  - *Prompt injection*: hidden instructions in content the model reads — faint text in an image, white-on-white text on a web page that makes Bing insert a phishing link, a shared Google Doc that tells Bard to exfiltrate data via image URLs (blocked by CSP, then bypassed through Apps Script writing into an attacker-readable doc).
  - *Data poisoning / backdoors*: a trigger phrase in fine-tuning data ("James Bond") corrupts outputs.
  - Defences exist and many specific attacks are patched, but the class persists.
- **For Sam:** the blog→trip pipeline reads **untrusted third-party web content** — treat every article as potential prompt injection. Never let article text decide tool calls or URLs. Extract into a strict schema, validate every place/URL against your own database/allowlist, and strip or flag instruction-like text. Never trust model-produced IDs, prices or coordinates without lookup (the ISBN lesson). Use the params×bytes rule to pick local models for the location-classification job.

## Hamel Husain & Shreya Shankar — Intro To Error Analysis: Creating Custom Data Annotation Apps (https://www.youtube.com/watch?v=qH1dZ8JLLdU)
**Before any metric, judge or framework: read outputs yourself in a friction-free custom viewer, write free-form notes, cluster them into failure modes, count them, and fix the most frequent ones first.**

- **Why.** Teams get stuck because they pick frameworks/vector DBs/agent libraries instead of looking at data. Without a structured way to find errors you play **whack-a-mole**: a prompt tweak fixes one thing and silently breaks another, and you can't tell if you're improving. Error analysis is an old ML technique for stochastic systems; it tells you what to work on (prompt? retrieval? something else?) and what to measure.
- **The process (iterative, repeated several times even before launch):**
  1. **Open coding**: look at input/output pairs one at a time and write free-form notes on what's wrong — do not pre-categorise, do not root-cause yet ("inferred the wrong experience", not "RAG is broken").
  2. **Axial coding**: group the notes into failure categories (an LLM can propose categories from your notes — tell it notes are chronological and later notes reflect updated thinking — then a second pass assigns each note to one or more categories).
  3. **Pivot table**: count errors per category; the counts set priorities.
  4. Fix (prompt, retrieval, pipeline), which may create new specific metrics; loop back. Over cycles new failure modes appear less often and the system stabilises.
- **Case study.** An "AI recruiter" (Llama 3 70B) writing personalised invitations from Kaggle resumes. Failures found in minutes: greeting uses a role ("Dear HR Manager") instead of name/blank; unfilled closing placeholder; **sender/recipient role confusion** (writing as the candidate applying rather than the recruiter inviting — they noted some models swap roles often); citing irrelevant resume parts; inventing skills not in the resume; rejection-sounding openings ("Although your background is mostly in..."); clichés ("impressed by your experience"); verbosity; repetition. None of these would be caught by generic metrics.
- **Build your own annotation app.** Shreya generated one live in minutes with an AI coding assistant (Flask + HTML): input (resume) on the left, output (email) rendered like an email in the centre, free-text feedback on the right, **arrow-key hotkeys** to move between rows, a persistent list of feedback written so far, a save/export button. While using it they wanted more: show the job posting, search the resume for phrases the model claimed, bigger feedback box. Why not spreadsheets or Label Studio: rendering the output as it will really appear (email, code, chart) removes mental translation; any framework is fine — pick one the AI codes well.
- **Rules of thumb.**
  - Do not ask an LLM to critique first — you'll anchor on its opinions and miss your own taste. Read at least ~10–20 yourself first; LLM judges come later to scale criteria you've already articulated.
  - Go slowly at first (minutes per example); one smoking-gun reason per output is enough.
  - Start with ~20–30 examples; **stop when 5–10 more reveal nothing new** (saturation).
  - Early on focus on critical notes; record positives when you want to preserve good behaviour or later build a judge.
  - Use voice dictation to cut annotation fatigue.
  - Generic metrics (helpfulness, conciseness, toxicity scores) are mostly useless and even harmful; measure the concrete failures you found.
  - If nearly every output in the first 20 is bad, go back to prompt engineering before building evals; otherwise write an LLM-judge per failure mode and run it on more data.
- **Criteria drift is normal.** Shreya flagged an "irrelevant hobby" as bad, then later liked a hobby mention phrased as a P.S. Your definition of good evolves while reading; keep notes in order.
- **For Sam:** build a tiny annotation app for the blog→trip pipeline: article rendered on the left with extracted places highlighted, generated trip/buttons in the centre, notes on the right, hotkeys, search-in-article to verify every claimed place. Do 30 articles of open coding, then cluster (likely categories: non-travel article passed the gate; place not in article; wrong place disambiguation such as same name in a different country; bookable product mismatched to place; missed places in listicles). The pivot-table counts tell you whether to fix the gate, extraction or matching first. Same method for location-row classification: sample 30 LLM labels per class, note errors, count.

## Jo Kristian Bergum (Vespa, hosted by Hamel Husain) — Back to Basics for RAG (https://www.youtube.com/watch?v=nc0BupOkrhI)
**The R in RAG is decades-old information retrieval: build your own small relevance-judgment set, measure every method against a BM25 baseline, prefer hybrid keyword+embedding search, chunk for precision, and remember real ranking uses more than text similarity.**

- **Demystify RAG.** It's just retrieving things to stuff into the prompt. Not only for Q&A: you can **retrieve similar labelled examples** (from a large annotated set) as few-shot context for an LLM classifier — retrieval-augmented labelling. Single-vector embeddings + an LLM is a naive RAG; retrieval is a deep field (web search, recommendations).
- **Evaluate retrieval as a black box.** Any method (BM25, vectors, hybrid, ColBERT, rerankers, even grep/NumPy) produces a ranked list per query; judge each (query, doc) pair as binary relevant/not or graded (0 irrelevant, 1 somewhat, 2 highly). Metrics:
  - **Recall@k**: fraction of all relevant docs found in top k — needs knowing all relevant docs, often impossible at scale.
  - **Precision@k**: share of top k that's relevant — easy to judge, not position-aware.
  - **nDCG**: uses graded labels and rewards relevant docs near the top.
  - **Reciprocal rank**: 1/position of first relevant hit (1st → 1, 2nd → 0.5).
  - "LGTM" (looks good to me) is the most common industry metric — do better. Online signals: clicks, dwell time, add-to-cart, revenue.
  - Query averages hide skew: ~20% of queries can carry ~80% of volume; weight accordingly.
- **Public benchmarks (MTEB, BEIR, MS MARCO) don't transfer to your domain.** Build your own relevance set: sample real user queries, spend a few hours judging results; pre-launch, have an LLM read your passages and write natural questions each would answer (synthetic queries). A plain **TSV of query_id, doc_id, label** is enough. Prefer a static document collection while evaluating (new docs entering the index shift rankings unnoticed).
- **LLM relevance judges work** (Microsoft/Bing research): with a good prompt, LLM query–passage relevance labels correlate well with humans. Validate on your gold set first — Jo used ~90 judged pairs from Vespa doc search and saw good agreement with GPT-4 — then judge at scale on sampled live queries, and quantify changes ("this change raised nDCG by 30%") instead of guessing.
- **Representations (why not score everything):** cross-scoring every doc (like a hosted reranker over the whole corpus) doesn't scale; you need an index for sub-linear retrieval, then rerank fewer candidates.
  - *Sparse*: vocabulary-sized vectors, non-zero only for present terms; inverted index with WAND/MaxScore (Elasticsearch-style); weights from corpus statistics (BM25) or learned by transformers (learned sparse).
  - *Dense*: text embeddings compared by distance in an ANN index — very fast at billion scale but approximate, and typically transfer-learned from someone else's data.
- **Embedding pitfalls.** Encoder models tokenise into a fixed (often 2018 BERT) vocabulary, then mean-pool token vectors into one vector → **dilution** for long text; new jargon/product names become out-of-vocabulary fragments and land in odd places (Vespa's "GGUF" support query failed). Precision drops beyond ~256 tokens per vector (Nils Reimers' guidance) → **you still need to chunk** for high-precision search (multi-vector-per-row indexing avoids splitting docs into many rows). Long-context embedding models are the wrong direction; larger vocabularies are the better one.
- **BM25 baseline.** Unsupervised, cheap, tiny index, no model inference, no out-of-vocabulary disasters. On a long-document (~3k tokens) benchmark where papers compared fancy embedding models, vanilla BM25 (Lucene/Vespa/ES) beat them. Downside: needs proper tokenisation/linguistics for CJK, Turkish, etc. (search engines provide it).
- **Hybrid.** Combining keyword and embedding retrieval covers exact tokens plus semantics, but it's not a silver bullet: kNN always returns neighbours, even far ones, so blind **reciprocal rank fusion can blend junk** into good keyword results. You need to know when to ignore embedding results — which your eval set tells you. No universal similarity threshold ("0.6 is bullshit — I don't know your queries").
- **Score calibration.** BM25, cosine and reranker scores have different ranges/distributions and aren't probabilities. Combining them is a learning problem: GBDT learning-to-rank over features (needs labels — your eval process generates them; LLMs can generate synthetic training labels), or at least a hyperparameter sweep scored on your eval set.
- **Rerankers / cross-encoders.** Feed query and document together for token-level interaction → higher accuracy, more compute. Use a funnel: cheap retrieval over many → expensive reranking over few, within the latency budget. **BM25 + reranker is a strong, safe starting point.** ColBERT (per-token vectors) is near reranker accuracy at higher serving cost but shares the vocabulary problem. Query expansion with LLMs helps somewhat but adds latency. Heavy jargon: hybrid, or pre-train your own tokenizer/encoder (e-commerce giants do).
- **Real-world ranking** uses many signals beyond text match: freshness, authority, quality, PageRank, revenue (Google leak). GBDT over tabular features + neural similarity features is effective. For domains like health, filter to authoritative sources via metadata.
- **For Sam:** matching extracted place names to a ~6M-row GeoNames/OSM master is a retrieval problem. Use BM25/keyword plus alternate names as the baseline, add metadata filters (country, admin1, feature class), then a reranker or LightGBM over features (name similarity, population, distance to other places in the article, feature code). Build a TSV gold set of ~100–200 (mention, correct geonameid) pairs and track MRR/precision@1 for every change. Retrieved labelled examples can also serve as few-shot context for the LLM location classifier.

## Zachary Blumenfeld (Neo4j) — Make Your AI Agents Predictable With Graph Engineering (https://www.youtube.com/watch?v=g_NgCLTibiM)
**Make agent work predictable by expressing it as an explicit graph — nodes do work, edges route state — and by compiling successful but variable agent runs into a deterministic, versioned "procedure graph" the agent executes via a CLI.**

(Vendor talk; the reusable ideas are framework-independent.)

- **Definition.** Graph engineering = designing agent work as an explicit graph. Not new (state machines, workflow graphs, knowledge graphs); new is applying it to agents. Three kinds:
  1. **Execution graphs** — workflow graphs of routers and agent nodes inside a harness (LangGraph, ADK, multi-agent orchestrators).
  2. **Context graphs** — stored decision traces (conversation = short-term memory, extracted entities = long-term memory, reasoning/tool-call traces) linked to your domain data.
  3. **Procedural graphs** — a procedure/skill as a graph whose steps can be scripts, decision models, validation steps, escalation routers, not necessarily agents.
- **Benefits.** Predictability (constrained path → consistent, accurate results), governance/audit (explicit steps, timestamps, provenance), portability (the graph is a stored artefact, not just runtime code, so any harness can run it).
- **Compile prose into structure.** Their research (workshop paper) converted a skill's markdown + scripts + references into a graph of decision points, routing points and scripts, turning prose instructions into deterministic scripts. Forcing the agent to follow the graph raised task reward on diverse hard tasks and let smaller models do the work.
- **Distil procedures from history.** Take the context graph of past successful (but inconsistent) runs and distil a graph-shaped skill (YAML) that stays linked back to the traces and source policy docs → every step has provenance, versions and drift tracking.
- **Loan-approval demo (pattern worth copying).**
  - Free-form agent: crawled business plan PDF + transaction data + lending policy + past decisions, produced a good audit-trailed answer, but run-to-run **paths differed in length and order**, nothing enforced the procedure, and approve/deny "confidence" scores were uncalibrated.
  - Compiled procedure:
    1. Deterministic **hard policy rules** → auto approve/deny.
    2. Otherwise a dedicated **decision model** (calibrated classifier) picks a risk tier.
    3. A router for **human escalation**.
    4. The LLM writes the report.
    5. A **lint/check loop** on the report.
  - The agent just calls "run skill" through a small CLI; routing is programmatic.
  - Result: wall clock roughly 7.5 min → ~2 min; the frontier model alone was accurate but slow and costly; with the procedure, a small model (Haiku-class) sufficed, cutting cost sharply.
- **Observability on graphs.** Persist each run as a path through the graph; query which branches were taken, never taken, or failed — great for governance and finding dead logic.
- **Use cases.** Compliance/audit reports across sources with entity resolution (tickers/names across databases); Uber-style configuration graphs encoding region-specific regulations from many microservices.
- **Rules of thumb.** Let the LLM explore first; once a task recurs, **move routing and rules out of the prompt into code**, keep the LLM for genuinely fuzzy steps (writing, judgment), put a calibrated model on numeric decisions, and keep traces linked to outputs.
- **For Sam:** the blog→trip pipeline should be a fixed graph, not a free agent: (1) LLM gate (or cheap classifier) "is this a travel article with bookable intent?" → (2) extraction to schema → (3) deterministic matching against the location master and supplier catalogues (Viator etc.) → (4) rules (availability, geography sanity, dedupe) → (5) LLM only for trip narrative → (6) validator/lint loop → (7) human review queue for low-confidence cases. Log every run's path to find which branches fail. The same "hard rules → calibrated model → LLM only for leftovers → escalate" shape fits the sanctions-screening side project too.

## Sayash Kapoor (AI Snake Oil, Princeton) — Building and evaluating AI Agents (https://www.youtube.com/watch?v=d5EltXhbcfA)
**Agents fail in the real world because evaluation is hard, static benchmarks mislead, and capability is confused with reliability; the AI engineer's job is reliability engineering around stochastic parts, with cost always measured alongside accuracy.**

- **Framing.** Agents (LLMs controlling a system's flow) already work as rudimentary components (chat apps with filters and tools; deep-research-style 30-minute reports), and will mostly appear as **small parts of larger systems**. The ambitious autonomous visions mostly haven't worked.
- **Reason 1: evaluating agents is genuinely hard.** Examples of failed claims:
  - DoNotPay ("robot lawyer") was fined by the FTC for false performance claims.
  - LexisNexis/Westlaw "hallucination-free" legal AI: Stanford found hallucinations in roughly 1/6 to 1/3 of cases, some reversing a source's meaning.
  - Sakana's "AI scientist" was tested on toy problems and judged by an LLM rather than peer review.
  - Sakana's CUDA-kernel agent claimed 150× speedups — 30× beyond the H100's theoretical maximum — because the agent **hacked the reward function**.
  - CORE-Bench (Princeton): reproduce a paper's results *given code and data* — the best agents managed <40%.
  - Treat evaluation as first-class, or you ship failures. Sanity-check results against physical/theoretical limits.
- **Reason 2: static benchmarks mislead for agents.**
  - LLM evals are string in → string out; agents act in environments, so evals need sandboxes.
  - LLM eval cost is bounded by the context window; agent cost is unbounded (loops, sub-agents, recursion) → **report cost next to accuracy; use Pareto frontiers**. On CORE-Bench a Claude 3.5 agent ≈ o1 accuracy at ~$57 vs ~$664 → pick the 10× cheaper one.
  - Agents are purpose-built, so one benchmark doesn't fit all; you need multi-dimensional, task-specific metrics. (Their Holistic Agent Leaderboard, HAL, runs cost-controlled evals across ~11 benchmarks.)
  - "Too cheap to meter?" Prices fell >100× from text-davinci-003 to GPT-4o-mini, but costs still bite at scale and in open prototyping, and **Jevons paradox** (cheaper units → much more usage, as with coal and ATMs/bank branches) means total spend grows.
  - Benchmark wins drive funding (SWE-bench → big rounds), yet an independent month-long trial of Devin succeeded at 3 of 20 real tasks.
  - Fix: "who validates the validators" (Shreya Shankar et al.): domain-expert humans in the loop who keep editing the criteria that LLM evaluators use.
- **Reason 3: capability ≠ reliability.** Capability ≈ pass@k for large k (it *can* get it right sometimes); reliability = right every time. Consequential deployments need reliability. Model training gets you to ~90%; closing the gap toward "five nines" is the AI engineer's job. A food-ordering assistant that's right 80% of the time is a catastrophic product (Humane Pin, Rabbit R1 failures).
- **Verifiers aren't a silver bullet.** Retry-until-a-verifier-passes (inference scaling) assumes perfect verifiers. HumanEval and MBPP unit tests have **false positives** (wrong code passes); accounting for them, accuracy-vs-attempts curves **bend downward** — more tries means more chances of a wrong answer slipping through. Check your verifier's false-positive rate.
- **Mindset.** AI engineering is a system-design / **reliability engineering** discipline: build software abstractions around inherently stochastic components. ENIAC precedent: ~17,000 vacuum tubes failing so often the machine was down about half the time; the engineers' first two years were spent on reliability until it was usable.
- **For Sam:** report cost per article and per 1k location rows next to accuracy for every model/prompt variant; pick from the Pareto frontier (a small model at 95% of quality for 10× less wins at millions of rows). Measure reliability, not best-of-N: run the same article several times and check consistency. If you add a validator-retry loop (e.g. "JSON valid and all places exist in the master table"), measure the validator's own false-positive rate, or retries will just launder errors. Beware the pipeline gaming its own metric (e.g. the gate passing everything if you only measure recall).

## Douwe Kiela (Contextual AI, co-creator of RAG) — RAG Agents in Prod: 10 Lessons We Learned (https://www.youtube.com/watch?v=kPL-6-9MVyA)
**Enterprise value depends on handling context, not on the model: build specialised systems over your own messy data, design for production from day one, ship early to real users, and manage the inevitable inaccuracy with attribution and observability.**

(Short, high-level talk; partly a vendor pitch. Lessons in order.)

- **Context paradox (Moravec-style).** LLMs do "hard" things (code, maths) well but struggle with what experts find easy: putting information in the right context. Value scales from convenience (general assistants) to differentiated business transformation, and the higher you aim the more context handling you need. Only ~1 in 4 businesses report value from AI (Forbes).
- **1. Systems over models.** The LLM is ~20% of an enterprise RAG system. A mediocre model with an excellent retrieval pipeline beats a great model with a poor one. Don't reset everything on each model release.
- **2. Expertise is fuel → specialise.** Capture institutional knowledge with systems specialised to a domain/use case ("specialisation over AGI") rather than generic assistants.
- **3. Data is the moat.** The company *is* its data long term. Don't wait to scrub everything clean; make AI work on **noisy data at scale** — hard, but that's where the advantage is.
- **4. Pilots are easy, production is hard.** A framework + a few documents + 10 friendly users is easy. Production means 10^4–10^6+ documents, thousands of users, many use cases, security/compliance. **Design for production from day one.**
- **5. Speed beats perfection.** Get a barely functional version to *real* (not friendly) users early, then hill-climb on their feedback; waiting for perfect makes pilot→production harder.
- **6. Don't let engineers do boring plumbing** (endlessly tuning chunking strategies, basic prompts) when it can be abstracted; spend their time on differentiated value.
- **7. Make AI easy to consume.** Many "in production" systems have ~zero users, neutered by risk reviews or unclear to users. Integrate into **existing workflows**.
- **8. Make it sticky — get to "wow" fast.** Design onboarding for the first aha moment (a Qualcomm engineer finding a forgotten 7-year-old document that answered long-standing questions).
- **9. Accuracy is table stakes; manage inaccuracy.** 90–95% may be achievable; enterprises worry about the missing 5–10%. Answer with observability, careful evaluation, **audit trails and attribution** (this answer came from this passage), and post-processing **claim checking** against sources — essential in regulated industries.
- **10. Be ambitious.** Projects fail more from aiming too low (a FAQ bot for vacation days) than too high; aim where the ROI is.
- **For Sam:** carry provenance through the blog→trip pipeline — every extracted place and trip item keeps the article sentence/offset it came from and the master-table/supplier ID it matched, so reviewers (and publishers) can audit and claims can be checked automatically. Ship the Drive Button to a few real publishers early and hill-climb rather than polishing a pilot. The location work (making the pipeline robust to noisy GeoNames/OSM rows rather than hand-cleaning) is the moat Douwe describes.

## Barry Zhang & Mahesh Murag (Anthropic) — Don't Build Agents, Build Skills Instead (https://www.youtube.com/watch?v=CEvIs9y1uog)
**One general agent (loop + bash + file system) is enough; what it lacks is domain expertise, so package expertise as "skills" — folders of instructions, scripts and assets, progressively disclosed — and combine them with MCP for connectivity.**

- **Shift.** They expected each domain to need its own bespoke agent. Instead, **code is the universal interface to the digital world**: Claude Code turned out to be a general agent (e.g. financial report = call APIs for data, organise files, analyse in Python, write the output file — all via code). Scaffolding can shrink to bash + file system. The missing piece is **expertise**: you'd rather have an experienced tax professional than a genius deriving the tax code from first principles — agents are brilliant but lack up-front context, can't absorb your expertise well, and don't learn over time.
- **What a skill is.** An organised folder packaging composable procedural knowledge: `SKILL.md` (instructions + directory of what's inside) plus scripts, references, assets. Deliberately simple: anyone (human or agent) can create one; versionable in git, shareable via Drive or zip.
- **Scripts as tools beat traditional tools.** Classic tool definitions can be ambiguous, the model can't fix them, and they sit in the context window permanently. Code is self-documenting, modifiable, and lives on disk until needed. Example: Claude kept rewriting the same Python to style slides → they had it save the script into the skill for its future self → more consistent and cheaper. **Rule: when the agent repeats the same code, freeze it into a script.**
- **Progressive disclosure protects context.** At runtime only skill metadata (name/description) is in context; the agent reads the full SKILL.md when it decides to use the skill, then opens other files only as needed → hundreds of skills can coexist. (So the description must say clearly when to use it.)
- **Ecosystem (weeks after launch, thousands of skills).**
  - Foundational skills: Office document creation; scientific skills (EHR analysis, bioinformatics libraries).
  - Partner skills for their own products: Browserbase/Stagehand browser automation; Notion workspace research.
  - Enterprise/team skills: org best practices, quirky internal software, code-style rules for thousands of developers.
  - Trends: skills are getting complex (binaries, executables; weeks to build and maintain); skills orchestrate multiple MCP tools (**MCP = connectivity to the outside world, skills = expertise**); non-engineers (finance, legal, recruiting, accounting) write skills.
- **Converging architecture.** Agent loop (manages tokens in/out of context) + runtime environment (file system, code execution) + MCP servers (external tools/data) + a skill library loaded on demand. New vertical = right MCP servers + right skills (how Anthropic launched financial-services and life-sciences offerings).
- **Open problems = treat skills like software.** Testing/evaluation (does the agent trigger the right skill at the right time? is output quality with the skill as expected?), versioning and lineage as behaviour changes, explicit dependencies on other skills/MCP servers/packages for predictable behaviour across runtimes.
- **Skills as continual learning.** The standard format guarantees anything Claude writes down can be used efficiently by a future instance → transferable learning; a concrete, procedural form of memory (not everything, just how-to). Cheap to add, evolve, and drop; in-context learning suits fast-changing knowledge. Goal: Claude on day 30 is much better than on day 1; a skill-creator skill already lets Claude write skills.
- **Stack analogy.** Models ≈ processors (huge investment, limited alone); agent runtime ≈ OS (orchestrates tokens/resources); skills ≈ applications where millions encode domain expertise.
- **For Sam:** this is directly the format he's building (backend/data-engineering/AI-engineering skills). Implications: write a sharp description (it's all the agent sees before loading); keep SKILL.md a lean index pointing to deeper reference files; move repeated code (GeoNames chunked loaders, supplier-API clients, eval harness) into scripts inside the skill; version skills in git and test that they trigger on the right prompts. For Trameter, one general agent + MCP for supplier APIs (Viator, RateHawk) + skills encoding booking-flow and location-matching know-how beats building separate bespoke agents.

## Barry Zhang (Anthropic) — How We Build Effective Agents (https://www.youtube.com/watch?v=D7_ipDqhtwk)
**Don't build agents for everything (workflows often win), keep an agent to its three essentials (environment, tools, system prompt) as long as possible, and debug by putting yourself inside the agent's limited context window.**

- **Progression.** Single calls (summarise, classify, extract — now table stakes) → **workflows** (multiple calls in a predefined control flow, trading cost/latency for quality; the start of agentic systems) → **agents** (choose their own trajectory from environment feedback). More agency = more useful, but more cost, latency, and consequences of errors.
- **Checklist: should this be an agent?**
  1. *Complexity*: agents shine in ambiguous problem spaces. If you can map the decision tree, build it explicitly and optimise each node — cheaper and more controllable.
  2. *Value*: exploration burns tokens. ~$0.10 per task budget ≈ 30–50k tokens — for high-volume support, use a workflow for the common scenarios and capture most of the value.
  3. *De-risk critical capabilities*: check the agent can do each essential step (a coding agent must write, debug, recover from errors); bottlenecks multiply cost and latency → reduce scope and retry.
  4. *Cost of errors and of discovering them*: high-stakes, hard-to-detect errors block autonomy; mitigate with read-only access or human-in-the-loop (at the cost of scale).
  - Coding passes all four: ambiguous (design doc → PR), valuable, models already good at the parts, and **verifiable via tests/CI**.
- **Keep it simple.** Agent = model using tools in a loop. Three components: **environment** (system it operates in), **tools** (interface to act and get feedback), **system prompt** (goals, constraints, ideal behaviour). Upfront complexity kills iteration speed; iterating on these three gives the highest ROI. Their very different agents share almost the same code — really only tools and prompt change. Optimise later: cache trajectories (coding/computer use) for cost, parallelise tool calls (search) for latency, show progress to build user trust.
- **Think like your agent.** At each step the model only sees ~10–20k tokens of context; complex behaviour is still inference on limited context. Exercise: do a computer-use task as the agent — a static screenshot, a vague prompt, act "with eyes closed" for 3–5 s, then a new screenshot. It reveals missing context (screen resolution, recommended actions, limitations/guardrails to avoid needless exploration). Use the model to critique itself: ask whether the system prompt is ambiguous, whether a tool description is usable (more/fewer params?), and feed it a whole trajectory asking "why did you decide this here, what would help you decide better?" — complements, not replaces, your own understanding.
- **Open questions (early 2025).** Budget-aware agents (enforce limits in time, money, tokens — unlike workflows, agent cost isn't controlled today); self-evolving tools (meta-tools where agents improve their own tool ergonomics); multi-agent collaboration in production (parallelism, separation of concerns, sub-agents protecting the main context window) with open problems around asynchronous agent-to-agent communication beyond rigid user/assistant turns.
- **For Sam:** by this checklist the blog→trip pipeline is a **workflow**, not an agent — the decision tree is mappable, volume is high, per-article budget is small, and errors (wrong bookable product) are costly and hard to spot. Same for million-row location classification: a fixed classify→validate flow. Reserve agentic loops for open-ended internal tasks (exploring a new supplier API, debugging data issues). When writing prompts and tool descriptions, paste them into the model and ask what's ambiguous; read failing traces as if you only had that context.
