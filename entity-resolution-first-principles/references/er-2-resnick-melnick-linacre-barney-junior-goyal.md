# er-2 — cross-cutting principles

1. **ER = estimate the missing unique ID.** Pipeline is always: standardise → block (candidate search) → compare fields at graded levels → score/classify pairs → cluster → evaluate → (fuse into golden record). Dedup and linkage are the same problem; linking = stacking datasets and deduping. [Linacre/Splink; Melnick/Spark-Graph; Security&Privacy Academy; Juvenal]
2. **Cleaning beats cleverness.** Strip accents (unidecode), case, punctuation, hyphens; set invalid placeholders to real NULL so they score 0 rather than agree. A plain edit ratio scored 0.16 on reordered tokens; token-sorted, accent-free comparison scored 1.0. [Resnick; Juvenal]
3. **Three evidence sources per field:** fuzzy similarity of the pair, term frequency (agreement on rare values is worth more than on common ones), and data quality (how often true matches *disagree*). Ignoring any one leaves accuracy on the table. [Linacre]
4. **Fellegi-Sunter maths:** m = P(agree|match), u = P(agree|non-match); agree weight log(m/u), disagree log((1−m)/(1−u)); sum + prior (e.g. 1/9000 ≈ −13 in log2) → match probability. u ≈ chance agreement from random pairs; m via EM when unlabelled. Additive weights are explainable (waterfall charts). [Resnick; Linacre]
5. **Respect conditional independence.** Nested fields (postcode within province; locality within admin region within country) double-count. Compare the child only if the parent agrees. Do not score low-information correlated fields (sex): partition the linkage by them instead. [Resnick]
6. **Graded comparison levels, not binary.** E.g. JW ≥ 0.85, then ≥ 0.90 conditional on passing 0.85; exact/phonetic/edit-1/inverted-name/temporal-distance levels as SQL CASE WHENs, each with a learned weight. [Resnick; Linacre; Barney]
7. **Blocking needs recall, not precision.** Use a union of several blocking rules/fingerprints, because any single key loses matches whose key is corrupted. Measure pair completeness (true matches kept) vs reduction ratio (pairs avoided). Count the comparisons a rule generates before running it. [Resnick; Linacre; Juvenal]
8. **Big blocks are data-quality bugs and supernodes.** "Sir"+"Baronet" created ~300k of 625k comparisons. Low-cardinality attributes (eye colour, generic tokens, placeholder phones) create supernodes and blow up graph queries. Inspect top block-generating values. [Linacre; Melnick]
9. **Fingerprint families for blocking:** sorted tokens, first-N tokens, prefix, acronym, phonetic code, q-grams, geohash for coordinates, magnitude for numbers. Approximate blocking via ANN/LSH. Learned blocking (dedupe, Zingg) chooses predicates that cover labelled matches cheaply; Zingg reports ~0.05% of Cartesian pairs. [Juvenal; Sonal Goyal; Melnick]
10. **Token rarity for organisation/place names.** Generic tokens repeat ("Inc", "Hospital"), so weight token agreement by rarity (TF-IDF-like). Use token-order-insensitive metrics (Monge-Elkan, token sort). [Resnick; Juvenal]
11. **Active learning solves the labelling problem.** Matches are a tiny fraction of pairs, so let the tool pick uncertain edge cases. About 50–60 labelled pairs starts a model (Zingg); include hard negatives. [Juvenal/dedupe; Goyal/Zingg]
12. **Always cluster after pairwise scoring.** Pairwise output is intransitive. Clustering (connected components or hierarchical) adds missed links and, with hierarchical methods, can drop weak ones. Evaluate on cluster-derived pairs. Connected components via GraphFrames `connectedComponents()` + groupBy to merge. ER is *micro-clustering* (millions of tiny clusters); k-means does not fit. [Juvenal; Melnick; Goyal]
13. **Thresholds follow downstream cost.** Three-way outcome: auto-match / clerical review / non-match. Conservative cutoffs bias rates (e.g. undercounted deaths). Option: minimise estimated type I + II, or weight analyses by match probability instead of cutting. Mailers tolerate errors; justice does not. Probabilistic scoring shrinks review from 100k to ~100. [Resnick; Barney]
14. **Error estimation has three routes,** each with a flaw: gold-standard subset (may be unrepresentative), model-based Σ(1−p) (valid only if independence holds), clerical review (humans cannot tell with common names). Prefer precision/recall/F over accuracy. [Resnick; Security&Privacy Academy]
15. **Use relational context.** Resolve strong entities first; "shares an already-resolved neighbour" becomes a feature for weak records. [Melnick]
16. **Scale by pushing SQL to a backend.** Splink on DuckDB: ~1M records on a laptop in about a minute; MoJ says up to ~1M needs nothing more. Spark for 100M–750M. Same settings on any backend. A full Splink run cost under £5 on Synapse. [Linacre; Barney]
17. **Keep lineage and cluster-quality signals.** Link source records to resolved ids for debugging over/under-merges. Store min/max pair score per cluster (Zingg's z_minScore/z_maxScore) to flag weak or chained clusters. [Melnick; Goyal]
18. **Start where data quality and overlap are high,** or with single-system dedup, to get fast, verifiable value. Then build incremental/real-time matching (new record → block against existing entities → attach). [Barney; Melnick; Juvenal]
19. **Privacy.** Quasi-identifiers combined re-identify people. DP does not fit microdata linkage. PPRL exists. Do not link people who do not want to be linked. [Security&Privacy Academy; Juvenal]

**Sam-specific synthesis:** for 6M GeoNames/OSM places on 16GB, use Splink+DuckDB with multi-pass blocking (country + geohash prefix *with neighbour cells*; country + name fingerprint/phonetic). Use comparison levels for name (exact → token-sort → JW 0.9/0.85 → q-gram), a custom haversine-band level, term-frequency adjustment on names, and hierarchical admin comparisons. Count comparisons per rule first, and treat generic tokens as supernodes. Cluster with connected components, alert on giant clusters, keep a lineage table. For supplier → master matching, use link_only / a dedupe-Gazetteer-style one-to-one approach.

## Dean Resnick (NORC, ex-US Census Bureau) — Record Linkage Methodology Under Fellegi-Sunter Paradigm, with Extensions (https://www.youtube.com/watch?v=j9DGihMM8vs)
**Fellegi-Sunter is simple, scalable and provably optimal under conditional independence, so most "enhancements" are about respecting that assumption: clean fields, frequency-weight rare values, nest dependent fields hierarchically, and choose blocking passes and cutoffs deliberately.**

- **Mental model.** Record linkage is data fusion *with uncertainty about identity*; if a clean shared unique key exists, it is just a join. Dedup (entity resolution) = linking a file to itself. Applies to persons, organisations, addresses. Terminology: a *match* is the truth (same entity); a *link* is your inference. Fellegi-Sunter (1969; method predates them, Newcombe) showed that summing log-likelihood weights is the optimal discriminator *if field agreements are independent given match status*. Bayesian linkage models are fuller but scale worse and have little mature software; FS wins on large files.
- **Mechanism.** For each comparison field: m = P(agree | match), u = P(agree | non-match). Agreement weight = log(m/u); disagreement weight = log((1−m)/(1−u)). Pair weight = sum across fields. Missing on either side → field contributes 0 (neither credit nor penalty), so invalid values *must* be set to a real missing value the software recognises.
  - Estimating m/u: (1) gold-standard labelled set; u can be approximated from random pairs (nearly all non-matches), but exclude known matches if match prevalence is high; (2) EM algorithm on unlabelled pairs (the default when no training data).
  - u is just "chance agreement": two different people both called John maybe ~1%; rare names far less.
- **Enhancements (each a reusable rule).**
  1. *Standardise/parse*: strip punctuation, one case, consistent hyphens, remove diacritics/apostrophes (map to the dominant alphabet), invalid → missing. Split multi-part names, generate variants (swap order for e.g. Asian names, try second given name as first).
  2. *Nickname tables, built parsimoniously*: only include pairs a string metric would miss (Rob/Robert already scores high; Bill/William does not).
  3. *Frequency-based weights*: agreement on a rare value (an unusual surname) is far stronger evidence than on David/John. The frequency weight is effectively a value-specific u probability, tabulated from value frequencies in one file.
  4. *Hierarchical (nested) variables*: postcode is nested in state/province, so agreement on both is not independent and double-counts. Fix: only compare the child if the parent agrees (set child to missing otherwise). Keep the parent because the child is sometimes missing. EM estimates the conditional weights fine. He warns that truly hierarchical variables treated as independent can give "pretty poor" linkage.
  5. *Graded string similarity as nested levels*: Jaro-Winkler (Jaro + Winkler, Census Bureau, public domain). Instead of binary agree/disagree: level 1 = JW ≥ 0.85 (agree/disagree weights); only if passed, test JW ≥ 0.90 with m/u *conditional on* already passing 0.85; and so on. Weights accumulate, which keeps FS assumptions rigorous. Thresholds are flexible; JW 0.80 can already signal similarity. Same trick for Soundex/NYSIIS (exact code vs. similar code levels). Dave vs David ~0.9.
  6. *Organisation names*: tokens repeat a lot ("Inc", "Hospital"), so weight each token's agreement by token rarity (TF-IDF-like). Directly relevant to place/supplier names ("Hotel", "Beach", "Airport").
- **Blocking.** 1M × 1M = 10^12 comparisons. Block on keys (e.g. first+last initials) and compare only within block. Any single key misses true matches whose key is corrupted → run *multiple blocking passes* with different keys (initials; full DOB) and union, keep best link. Trade-off: *pair completeness* (share of true matches surviving blocking = the real quality metric) vs *reduction ratio* (share of pairs skipped = compute cost only). Use a *sequential coverage algorithm* to choose the number of passes and keys rather than guessing.
- **Evaluating error.**
  - Gold standard subset (e.g. records with SSN): unlinked same-SSN pairs → type II (false non-match) rate; linked pairs with differing SSN → type I (false match) rate. Gotcha: the subset having the ID may differ systematically from the rest, biasing estimates.
  - Model-based: from match probabilities, expected false links = Σ(1 − p) over accepted links; analogous formula for missed matches. Validated against gold standards and often good, but only valid if the independence assumption holds; check it first.
  - Clerical review of a sample of links: easy to explain, but humans cannot tell with common names; unreliable. He prefers model-based when assumptions are verified.
- **Cutoffs.** Threshold on weight or match probability (e.g. p > 0.90). No theory for the best value; it depends on downstream use. Too conservative undercounts (death rates biased low when the death file is the linked source); for regression, a high-confidence subset may be better. One option: minimise estimated type I + type II; practical issue is that similar projects end up with different cutoffs, confusing users. Alternative: no hard cutoff; weight analyses by match probability. Q&A: forcing exact SSN agreement gives very low type I but high type II and biases the linked population toward people with good SSNs. Weight errors by their downstream cost.
- **Correlated fields (sex/gender).** Sex agreement is highly dependent on first-name agreement, carries little information (~50% chance agreement), and changes the m of other fields (women's surnames change on marriage). Rule: do not score it; *split the linkage into separate passes by the stratifying field*, duplicating records with missing/non-binary values into both passes. General lesson: use a correlated or low-information field to partition, not to score.
- **Software.** SAS custom code and package "NORC Link": EM, match probabilities, JW, nicknames, frequency weights, hierarchical weights. Bayesian alternatives lack software.
- **For Sam.** Places: country → admin1 → admin2 → locality are nested, so use hierarchical comparisons (compare admin1 only if country agrees) rather than summing independent weights. Weight name-token agreement by token rarity, since generic words like "Hotel" or "Airport" are common. Use graded JW levels for names. For 6M GeoNames/OSM, use multiple blocking passes (e.g. country+geohash cell; country+name prefix/phonetic) and measure pair completeness on a labelled sample. Partition by feature class or country rather than scoring it, if it is used as a hard constraint.

## Max Melnick (Deloitte) — Massive Scale Entity Resolution Using the Power of Apache Spark and Graph (https://www.youtube.com/watch?v=IOMM7wSYeFE)
**ER is three problems (search for candidates, classify pairs, aggregate into entities). Model records and their attributes as a graph to get schema-flexible blocking, connected-components clustering and relational context, but watch for supernodes and do not force graph where SQL or a search engine fits.**

- **Mental model.** Motivating case: two merged airlines, same passenger written as "John A Doe" vs "John Doe", IATA codes vs airline names, different date formats. Every multi-source analytics use case (fraud, customer 360, KYC) needs one deduplicated view first. ER pipeline: (1) *search / candidate selection* (blocking), because you cannot compare every record to every record at scale; (2) *comparison / classification* (anything from weighted attribute scoring with a threshold to an ML classifier) producing "same-as" pairs with some certainty; (3) *aggregation / canonicalisation* into a resolved entity (merge attributes, e.g. union two different emails).
- **Three hard parts.** Vertical scale (more data). "Horizontal" scale: adapting when sources add fields or change representation. Data quality: when the blocking key or a model feature is missing, a candidate cannot be found or confidently classified.
- **Why Spark + graph.** Spark = scale and connectors for many source formats. Graph = flexible data model for heterogeneous data, variable-hop queries (shortest path), and relationship context. Tools: Spark GraphFrames (motif finding, connected components, PageRank, community detection) plus a graph DB (DataStax Graph) for user queries. GraphFrames is just two DataFrames (vertices, edges).
- **Pattern 1: graph-based candidate selection.** Model entity vertices (customer) linked to attribute vertices (phone, email, address). One motif query "two customers sharing any attribute vertex" returns candidate pairs. With SQL, each new blocking attribute needs a rewritten join/union. With the graph, the query is unchanged; you only add vertices/edges. This is multi-pass blocking done as "shared-value" joins.
- **Pattern 2: clustering via connected components.** Put the classifier's same-as pairs into a GraphFrame, run `connectedComponents()`, get a component id per record = resolved entity id, then `groupBy(component).agg(...)` to merge attributes (collect sets of emails/phones). Standard transitive closure step. (note: connected components can chain false positives into giant clusters; the talk does not discuss safeguards. See other notes on cluster-level checks.)
- **Pattern 3: relational context for weak records.** Applications contain an applicant (rich identifiers, easy to resolve) and a point of contact (only name + phone). Two "John Doe" contacts with the same name/phone are weak evidence alone. If both attach to the *same already-resolved applicant*, that shared neighbour is extra evidence. Find this with a motif query and feed "shares a resolved neighbour" as a feature into the match model. This is collective/iterative ER: resolve strong entities first, then use them as context for weak ones.
- **Gotchas.**
  - *Supernodes*: high-degree vertices kill query performance and make visualisation unreadable. In ER graphs they come from low-cardinality attributes (eye colour, the "Hotel" token, a default phone like 000-000, a placeholder email). Do not make such attributes vertices; store them as properties or drop them. The same applies to blocking keys: very frequent values create huge blocks.
  - Graph tooling is immature compared with SQL: fewer resources, weaker streaming support, out-of-memory errors in community-detection algorithms. Start small, then scale up, because hidden data-quality issues and supernodes appear at scale.
  - Graph is not a silver bullet. Fuzzy search or programmatic indexes → search engine. Static joins on homogeneous data → SQL. The sweet spot is hybrid.
- **Tips.** Persist the graph at scale (vertices/edges to Parquet if only analysts use it; a graph DB if apps need point queries). Use a visual tool to debug subgraphs; edge tables are hard to read. Keep lineage: link source/transactional records to the resolved entity so over-merges and under-merges can be debugged and users can see why records were merged (Q&A answer on validation).
- **Incremental.** Full reloads stop working at scale. They built an update path where new records run through blocking/search against existing entities, then get attached. Team also tried locality-sensitive hashing (LSH) for candidate search.
- **For Sam.** On a 16GB laptop the same patterns work without Spark: build an edge list of matched pairs and run connected components with DuckDB recursive CTE / union-find in Python / networkx or igraph on the edges only. Treat common tokens in place names, shared generic coordinates (0,0; country centroids) and placeholder phone numbers as supernode risks; cap block sizes. Pattern 3 maps well to places: a POI matched to the same resolved city or airport strengthens weak name matches. Keep a source_record → entity_id lineage table.

## Robin Linacre (UK Ministry of Justice, Splink lead) — Rapid deduplication and fuzzy matching of large datasets using Splink (https://www.youtube.com/watch?v=eQtFkI8f02U)
**A pairwise match probability needs three kinds of evidence (fuzzy similarity, term frequency, and per-field data quality / evidence from mismatch). Fellegi-Sunter learns how to combine them from unlabelled data. Splink adds fast SQL backends, blocking diagnostics and explainable charts so this runs on 100M+ records.**

- **Problem framing.** Data about the same entity, collected without a unique ID, within one dataset (dedup) or across datasets (linkage). Same maths for both. Without an ID you cannot even answer "how many people are there?". Goal: *estimate the missing ID column*. Pipeline: generate pairwise comparisons → predict match probability per pair → treat records as nodes and probabilities as edges → cluster (connected components above a threshold) → cluster id = entity id.
- **Splink positioning.** Free/OSS, Fellegi-Sunter based. Built because free libraries choked beyond ~100k records and MoJ had ~100M. Same core method as others, much faster: about 1M records on a laptop in about a minute. It pushes heavy computation into a SQL backend (DuckDB locally, Spark, plus others), so scaling is the backend's job. Unsupervised training (labelled data is rare); supervised also supported. Heavy investment in diagnostic charts to avoid black-box decisions affecting citizens. Used by ONS (2021 census, Inter-Departmental Business Register), German stats office, EMA, Chilean health ministry, Australian ABS contributors. 9M+ downloads.
- **Three information sources (key mental model).**
  1. *Fuzzy similarity* (Levenshtein = edit count, e.g. Smith/Smyth = 1; Jaro-Winkler 0–1): looks only at the two values in isolation.
  2. *Term frequency / coincidence*: an exact or fuzzy match on a common value (Smith) is weaker evidence than on a rare value (Linacre), because random different people share common values by chance. Comes from the whole dataset, not the pair. Generalises to fuzzy matches ("how often do two random people have names 1 edit apart?").
  3. *Data quality / evidence in mismatches*: how often values differ *among true matches*. A 1-vs-7 month typo in hand-keyed data is expected (weak evidence against or even net evidence for), but in a highly reliable DOB field it is strong evidence against. Most often forgotten and discarded. Many systems use only 1 or 2 sources and lose accuracy.
  - Fellegi-Sunter weights all three from the data, so nobody sets arbitrary weights like "exact first name vs DOB Levenshtein 1".
- **Worked flow (50k synthetic "historical people" dataset built into Splink).**
  1. *Profile columns first*: nulls (0.1% first-name null), skew (many Williams/Johns, long tail), junk values ("Sir" as first name), typos in the rare tail. Loop back to cleaning.
  2. *Blocking*: 50k records → 2.5 billion pairs, too many. Blocking quickly rejects obvious non-matches; it needs **high recall, not precision**, because scoring decides later. Splink *counts comparisons a rule would generate before running it* (first_name equality → ~16M), preventing a "50 trillion comparisons" blow-up. Use a *union of several rules* (a single first-name rule loses nickname/typo matches). Combined set gave ~625k comparisons. Charts show which rule dominates and which *specific values* create most pairs: "Sir" + "Baronet" alone made ~300k comparisons → a data-quality fix shrinks the blocks. Block-size skew is a data-quality signal.
  3. *Comparisons*: per column define ordered *levels of similarity*, each getting its own learned weight. DOB: exact / one-char typo / within N days/years (temporal). Names: exact / phonetic / JW thresholds. Out-of-box comparison templates exist; customise freely. Custom levels are SQL CASE-WHEN expressions, e.g. a "name inversion" level (first and surname swapped) gets its own weight.
  4. *Train*: unsupervised (estimate u from random pairs, m via EM, prior / λ) or supervised if labels exist.
  5. *Inspect*: **waterfall chart** per pair. Prior: P(random pair is match) ≈ 1/9000 → match weight −13.1 (log2 Bayes factor). Then add: exact full name +11.4; fuzzy DOB +3.6; exact postcode +12.3; birthplace "West Devon" vs "Devon" counted as non-match −2.6 (a simple model's miss that a smarter comparison level would fix); occupation "politician" small positive with a *negative term-frequency adjustment* because it is common. Total +14.8 → near-certain. **Match weights chart** shows every level's weight for every column, i.e. the whole model. Because the model is additive in log space, it is easy to explain.
  6. *Predict + cluster* → estimated cluster id column; join any tables on it and count entities once.
  7. *Accuracy*: with some labels, a dashboard shows FP/FN as the threshold moves.
- **Link types.** `dedupe_only`, `link_only` (only cross-dataset pairs), `link_and_dedupe` (several datasets, each with internal dups; MoJ links 7+ datasets this way). Linking is equivalent to stacking the dataframes and deduplicating.
- **Rules of thumb.** Profile → clean → design blocking with comparison counts → design graded comparison levels → train unsupervised → read the weights charts for sanity → threshold → cluster → evaluate on labels. Look at the values creating the biggest blocks. Model the actual error types in your data (inversions, typos, nicknames) as explicit levels.
- **For Sam.** DuckDB backend on a 16GB laptop matches his constraints. 6M places: block on e.g. country + geohash prefix, or country + name token / phonetic, and *count comparisons before running*. Inspect the top block-generating values (e.g. names like "Church", "School", "Bus Stop") and treat them as data-quality / supernode issues. Add a distance comparison level (custom SQL using haversine bands: <100m, <1km, <10km) and term-frequency adjustments on names. "West Devon vs Devon" is analogous to "Lagos" vs "Lagos State"; add a token-subset level. Use `link_only` for supplier-to-master matching and `link_and_dedupe` when suppliers also have internal duplicates.

## Barney (Simpson Associates, ex local-government/NHS analyst) — Mastering Record Linkage with Splink (https://www.youtube.com/watch?v=C6HOItmlv8A)
**A practitioner's case for probabilistic linkage. Hand-written deterministic and fuzzy rules plateau and turn into endless arguments about rule priority. Splink replaces that with learned per-level weights that sum to a score, which leaves a small grey zone for humans. Start with high-quality, high-overlap sources or single-system dedup.**

- **Progression of approaches (useful mental model).**
  1. *Deterministic*: exact first + last + DOB + address in SQL. Gets about 60% of true matches.
  2. *Hand-tuned fuzzy rules*: add Soundex, Jaro-Winkler, Levenshtein ("surname exact AND first name within 1 edit"). Climbs to roughly 80–90%, but needs ever more rules, takes years, and you cannot settle whether "exact first + fuzzy last" beats "fuzzy first + exact last".
  3. *Probabilistic (Splink/Fellegi-Sunter)*: declare all comparison levels per field up front (exact → several graded fuzzy levels → different). The data (plus any partial labels, e.g. NHS number on some records, and known non-matches) gives each level a weight (positive or negative evidence). Weights sum per pair. Reaches the same accuracy as an exhaustive rule set without the bikeshedding.
  - Example of graded similarity: Barney / Barny (1 edit) / Barnie (2 edits) / Barnabas (shares the prefix; nickname) / "Bernie" (ASR-style error). Each should be a different level, not a binary match.
- **Score bands → three outcomes.** High weight = auto-match, low/negative = auto-non-match, middle = grey zone. How you treat the grey zone depends on the *cost of error*: marketing mailers tolerate mistakes; justice/police decisions do not. Send the grey zone to clerical review. Probabilistic scoring shrinks a 100,000-record manual job to about 100.
- **Splink history/requirements (MoJ).** Needed: cheap, accurate at ~100M rows (whole UK population plus duplicates), explainable to non-technical stakeholders, and portable (develop locally, run big in the cloud). Nothing on the market met this, so it was built with roughly £60k of government open-source funding.
- **Case study: Supporting Families programme (UK).** Link schools (attendance, exclusions), social care contacts, police (domestic violence), and benefits/unemployment data. No single signal flags risk, but three or more indicators qualify a family for early-intervention funding, with a later payment for measured improvement. Linkage turned scattered weak signals into an actionable combined view. This is the general value of ER: joining weak evidence across systems.
- **Where to start (rules of thumb).**
  - Pick sources with *high data quality* (schools update names/addresses constantly; social care addresses go stale once contact ends; ad-hoc spreadsheets are often unmatchable) and *high expected overlap* (schools ↔ social care: almost every child should be in both). Two small sources have few overlaps, so little value and hard to validate.
  - *Single-system dedup* is a fast win: one schema, and duplicates arise from operational shortcuts (call centre creates a new record in an emergency instead of searching). A known system with existing shaping queries can feed hundreds of found duplicates back to source within days.
- **Backends / scale.** Splink generates SQL; a backend executes it. DuckDB in-process on a decent laptop: MoJ guidance is that ~1M records needs nothing beyond DuckDB. Also Postgres, Athena/AWS, etc. Spark for ~100M; one US company dedupes ~750M product rows with it. Simpson typically uses 4–5 node clusters with 4–5 cores each. Same settings and logic regardless of backend.
- **Cost.** Commercial MDM: about £30k/yr to £100k+/yr, but includes UI, standardisation tooling, auditability. Splink is narrow (matching only) but nearly free: a full run on Azure Synapse cost under £5.
- **For Sam.** The deterministic → fuzzy rules → probabilistic progression mirrors typical hand-rolled place matching; move to learned levels once rules multiply. Start with the highest-quality, highest-overlap pair (e.g. supplier destinations ↔ GeoNames cities with population > N, or airports via IATA) before messy POI data. Size the grey zone by business cost: a wrong booking destination is expensive, a wrong blog-button suggestion is cheap.

## Flávio Juvenal da Silva Junior (Vinta) — 1 + 1 = 1 or Record Deduplication with Python (https://www.youtube.com/watch?v=eMI8lwQl3Dc)
**A hands-on end-to-end dedup on restaurant data: clean and choose order-insensitive similarity, geocode and use distance, block with fingerprints, train with active learning (dedupe), threshold, then *cluster* (transitive closure), which both adds missed links and removes some false ones.**

- **Similarity choices (concrete).**
  - Plain edit-distance ratio on two names of the same restaurant with words in a different order gave only **0.16**, so it is useless for reordered tokens.
  - *Token-based* similarity (Monge-Elkan from py_stringmatching: best inner similarity per token pair, averaged) ignores token order and scored high.
  - *Normalise first*: `unidecode` strips accents (café→cafe) and lifts the score to 1.0. Cleaning beats a cleverer metric.
  - *Addresses → geocode → distance*: geocode (geopy; Google or free geocoders) to lat/lon, then haversine km. "Close enough" = match evidence. Geocoders also return postal codes, which are useful as a blocking key.
- **Naive pipeline.** `itertools.combinations(ids, 2)` gives all pairs (6 records → 15 pairs). Represent each as a pair of record dicts; a comparison function returns {name_sim, distance_km}. Rule: name_sim ≥ 0.5 AND distance < 1 km found exactly the right pairs on the toy set. Rules can work on small data; larger, complex data needs a learned classifier.
- **Why blocking.** n(n−1)/2 grows quadratically: 1M records → ~500 billion pairs. Blocking yields only plausible candidate pairs.
- **Fingerprint blocking.** A fingerprint function normalises away irrelevant variation: unidecode → lowercase → split tokens → sort tokens → drop non-alphanumerics → join. Group by fingerprint, so different spellings with the same tokens share a block (and on the toy data, the blocks *were* the matches). Fingerprint families:
  - sorted tokens; a shared common token; first N tokens; prefix; acronym; phonetic code (works very well on some datasets); n-grams; **geohash** for coordinates; order of magnitude for numbers.
  - Records may emit *multiple fingerprints* (multi-pass blocking).
  - Exact fingerprints cannot bring together near-but-not-equal variants → *approximate blocking*: approximate nearest neighbours, **locality-sensitive hashing** (a hash designed to *maximise* collisions for similar inputs, the opposite of cryptographic hashing). He calls this a challenging research area.
- **Active learning with `dedupe`.** Labelling is hard because matches are a tiny fraction of pairs, and random sampling yields almost no positives. Active learning makes the library choose informative pairs to show you (CLI: y/n/unsure). Dataset: Fodors-Zagat restaurants, ~864 records with 150 true duplicate pairs (cluster column gives ground truth). He dropped phone and type to make it harder, geocoded addresses and added postcode. Field types: name String, address String, LatLong, postcode Exact. Label until tired, or until the questions look representative. Show non-matches too (same street and coordinates but different name = not a match).
  - **Learned blocking**: after training, inspect which predicates dedupe chose: (first token of name AND first 7 chars of name) OR (exact postcode AND first integer of address, i.e. street number). It picks from a built-in library of predicates to *cover labelled matches with the fewest comparisons*. This is a sanity check that you labelled enough.
  - Scoring: blocked pairs → per-field distances → classifier (logistic regression by default; he showed random forest) → a 0–1 score per pair. Threshold (0.5 here) trades precision vs recall. Result: high TP, only 3 FP, 11 FN.
- **Clustering is the missing step in most tutorials.** Pairwise output can be intransitive (A=B, B=C, A≠C). Compute clusters (`dedupe.partition` does hierarchical clustering over scored pairs) and derive pairs from clusters. On this data, clustered pairs had *more* true positives and *one fewer* false positive than raw thresholded pairs. Inspection: in one 4-record true entity, a missing edge was *added* by clustering. In a no-match neighbourhood of similar records, clustering *removed* one spurious edge but kept another. Clustering resolves ambiguity and improves results but cannot fix every FP. (note: dedupe uses hierarchical/centroid-style clustering, not pure connected components; pure connected components would only add edges, never remove them.)
- **Next steps he lists.** Other preprocessing, indexing and classifier options (Peter Christen's book *Data Matching*); **data fusion** (building the golden record from a cluster); **incremental record linkage** for new arrivals (dedupe's Gazetteer class for matching new records to a canonical set); **privacy**: differential privacy and privacy-preserving linkage. Ethical warning: do not link people who do not want to be linked; he used restaurants, not people, on purpose.
- **For Sam.** This is almost exactly Sam's place problem: normalise (unidecode, lowercase, sort tokens), use a token-order-insensitive name metric, and add haversine distance. Block with geohash prefixes (use neighbour cells too, so pairs across cell borders are not lost) plus a name fingerprint. Use dedupe's Gazetteer pattern for supplier listing → master place matching (one-to-one into a clean canonical set). Use active learning to build a labelled set cheaply. Always cluster, then evaluate at the cluster level.

## Sonal Goyal (Zingg founder) — Entity Resolution with Open Source Zingg (https://www.youtube.com/watch?v=F5Dw1QH0idQ)
**Zingg is an ML-first, rule-free ER framework on Spark: active learning builds a small training set, a learned blocking model cuts comparisons to ~0.05% of the Cartesian product, a pairwise classifier scores pairs, and graph processing produces cluster ids.**

- **Problem.** Customer, supplier, location, product and part data is spread over many systems (SaaS tools, M&A, legacy plus modern, departmental silos) with different schemas and validation rules. Without resolution, five records of one customer count as five customers, which breaks CLV, churn, personalisation, compliance and supplier consolidation. ER = building the missing unique identifier.
- **Two core difficulties.** (1) *Defining match logic* across heterogeneous attributes: hand rules are slow, complex and inaccurate. (2) *Scale*: no key means a Cartesian product. 10k records → 10k × 9,999 comparisons, and 10× more data gives 100× more comparisons.
- **Design goals.** Handle many entity types (customers, suppliers, addresses, organisations) without hand-coded rules. Scale to multi-million rows. ML learns the patterns from training data.
- **Why not standard clustering.** k-means etc. need k in advance and assume few large clusters. ER is *micro-clustering*: in 20M records, a given entity has maybe 5–6 records, and there are millions of tiny clusters. So they built custom learned blocking plus pairwise matching plus graph clustering, distributed on Spark.
- **Active learning for training data.** Training-set creation is a leading cause of ML project failure. Zingg picks *representative edge cases* (uncertain pairs) for the user to label match / non-match / unsure. A useful set starts around **50–60 labelled pairs** (matches + non-matches), with more non-matches since they dominate.
- **Model stack.**
  1. *Blocking model*, learned from labels: partitions records so only ~**0.05%** of all possible pairs are compared; runs distributed on Spark.
  2. *Similarity model*: a classifier over per-attribute features (distances/similarity metrics chosen by field type) within each block.
  3. *Graph processing* over scored pairs → clusters.
  - Output adds three columns: `z_minScore`, `z_maxScore`, `z_cluster`. The min/max of a record's pair scores within its cluster are useful for triage: a low min score flags weakly attached records or possible over-merges.
- **Case study.** North Carolina campaign-finance donors: messy, multi-source donor names. Before ER, one firm (GMMB Inc) appeared to contribute ~$28k; after resolution its true total was far higher. Unresolved entities bias aggregates *downward* per entity and inflate entity counts.
- **Gotchas implied.** Labels must cover hard negatives (similar-looking non-matches), otherwise blocking and classifier are too permissive. A learned blocking model is only as good as label coverage.
- **For Sam.** Zingg (Spark, local mode works) is an alternative to Splink when per-field Fellegi-Sunter independence is badly violated, for example place names whose meaning depends on category and country. Its min/max score columns are a cheap cluster-quality check worth copying in any pipeline (store min edge weight per cluster). Expect micro-clusters: most of Sam's 6M places should be singletons or tiny clusters, so a giant cluster is a bug signal.

## Security and Privacy Academy — Record Linkage Explained (https://www.youtube.com/watch?v=WbjC4ikuWi4)
**A short textbook overview of the canonical pipeline (preprocess → index/block → compare → classify → evaluate), framed from a privacy angle: linking quasi-identifiers creates re-identification risk, motivating privacy-preserving record linkage (PPRL).**

- **Definitions.** Record linkage (data matching) = combining data about the same object across databases to build a *microdata* set (individual-level). Applied to one database it is dedup, which improves data quality. Typical sources: census-scale data covering whole populations, useful for hard-to-survey subgroups but thin on demographics (income, education), hence linking. Privacy tension (quoting Paul Ohm's argument): data can be useful or perfectly anonymous, never both.
- **Quasi-identifiers.** Usually no person ID; you link on quasi-identifiers (DOB, ZIP, and at millions-scale even the name) that do not identify alone but do in combination; same concept as k-anonymity. Names are error-prone (Kane/Cane, Kristen/Christen), so you need fuzzy methods.
- **Pipeline.**
  1. *Preprocessing*: encode names uniformly across sources (umlauts, odd characters).
  2. *Indexing / blocking*: produce candidate record pairs instead of A×B. Blocking key splits data into blocks of similar values (phonetic codes such as Kane/Cane together; zip; city). Assumption: true matches share at least one blocking key. Trade-off: big blocks = more comparisons (slow); small blocks = missed matches. Block size often set by domain experts (analogous to choosing k in k-anonymity).
  3. *Comparison*: exact or approximate. Similarity functions map to 0–1, e.g. **q-grams** (substrings of length q; count shared q-grams; with q=2, the bigrams two strings share drive the score).
  4. *Classification*: comparison (similarity) vectors → match / non-match / *possible match* (three-way), via thresholds, probabilities, rules, or ML.
  5. *Evaluation*: efficiency (blocking cost) and effectiveness (accuracy, precision, recall, F-measure). Done during development on labelled data, since production has no ground truth. (note: accuracy is misleading in ER because non-matches dominate; prefer precision/recall/F on matches.)
- **PPRL.** Linking without seeing plaintext identifiers. Differential privacy does *not* fit directly because linkage needs individual-level records while DP protects aggregates. (Usual PPRL techniques such as Bloom-filter encodings of q-grams are not covered here; a follow-up video was promised.)
- **For Sam.** Mostly confirms the standard pipeline. Q-gram (bigram/trigram) similarity and q-gram blocking are cheap and robust for multilingual place names. Keep the three-way classification (match / review / non-match) in design. PPRL matters little for places but would apply if Trameter ever links traveller or customer identities with partners.
ules of thumb
  - Do the back-of-envelope: n²/2 × cost per comparison before designing anything.
  - Use precision/recall on matches, never overall accuracy.
  - Test with synthetic data whose cluster-size distribution resembles reality (large clusters stress clustering and blocking).
  - Plan for deltas (add/delete/modify) and stable entity IDs from day one.
- Failure modes & gotchas
  - Underestimating cluster sizes in test data → over-optimistic performance.
  - Re-running from scratch each time changes entity IDs, breaking downstream consumers.
  - Silent model decay with no monitoring.
- Relevance to Sam
  - 6M places all-pairs ≈ 1.8×10^13 comparisons — impossible on a laptop; must block (country + geohash/grid cell + name token) to bring it to ~10^7–10^8 pairs.
  - Supplier-to-destination matching is extremely imbalanced; evaluate with precision/recall on a labelled sample, and stratify the sample (by country, place type) so rare positives appear.
  - Trameter's master location IDs must stay stable across re-runs: carry forward IDs by maximum overlap between old and new clusters (survivorship), and process supplier deltas incrementally.
