# geo-2 — cross-cutting principles

1. **Query data where it lives; download only the slice you need.** Big open datasets (Overture ~200 GB, billions of rows) are published as cloud-hosted columnar files, not "download all" links. Filter by bbox/attributes with DuckDB/Athena and export just the region. [Anderson/Overture; Barron/GeoParquet]
2. **"Cloud-native" means small addressable chunks plus a table of contents.** COG tiles, Zarr chunks, Parquet row groups: a reader fetches the index, then range-requests only the chunks it needs, and parallel workers read different chunks at once. [Hanson FOSS4G 2022/2023; Barron]
3. **Spatial pruning in GeoParquet only works on spatially sorted data.** The bbox covering column gives per-row-group min/max; with random row order every group spans the globe and nothing is skipped. Sort by Hilbert/geohash before writing; use ZSTD; GeoParquet for analysis, PMTiles for display. [Barron]
4. **Partitioning (coarse, per chunk) is not indexing (fine, per row).** GeoParquet partitions scale to billions of rows; FlatGeobuf/GeoPackage/DuckDB R-tree index every row for fast small lookups. Pick by access pattern. [Barron; Gabrielsson/DuckDB]
5. **Two-stage spatial filter:** cheap bbox predicate first (stats/index), then the exact predicate (ST_Contains/ST_Intersects/distance). [Anderson; Gabrielsson; Barron]
6. **Check the CRS before every spatial operation.** Mismatched CRSs give wrong answers or errors; convert one side with `to_crs`/`ST_Transform`. Mind lon/lat axis order (`ST_Point(lon, lat)`), and use a projected CRS or spheroid functions for metres. [Soma; Gabrielsson]
7. **A spatial join is a join on a geometric predicate.** The left table keeps its geometry and the right table adds attributes. Use `how="left"` to see unmatched points (offshore, border gaps), and watch for duplicate rows from overlapping or shared-border polygons. [Soma]
8. **Broadcast the small side.** For lopsided joins (hundreds or thousands of polygons/destinations against millions or billions of points), copy the small table to every worker, or keep it in memory and stream the big side in chunks. [Forrest/Sedona]
9. **Use the simplest engine that copes; scale up only at diminishing returns.** GeoPandas/DuckDB/PostGIS first. Sedona/Spark only for planet-scale or complex overlays (zonal stats, area-weighted interpolation), because cluster overhead makes it slower on medium data. [Forrest; Gabrielsson]
10. **Keep pipeline state in a database or catalog, not a zoo of `final_v2.csv` files.** A DuckDB file gives transactions, joins and durability. Write steps as "metadata in, metadata out" and record lineage/version (derived_from), not dates in filenames. [Gabrielsson; Hanson]
11. **Validate geometries.** Simple-features invariants (holes inside shells, etc.) are not enforced on every op; invalid input gives undefined results. Run `ST_IsValid`/`ST_MakeValid` before overlays and joins. [Gabrielsson]
12. **Conflate with an explicit precedence and per-attribute provenance.** E.g. OSM (human-validated) > community > ML gap-fill, plus a `sources` array saying which source supplied each attribute. Push fixes upstream so they flow down. [Anderson]
13. **Ship confidence, not just filtered data.** Overture places carry a 0–1 existence confidence. Zero is a useful "no longer exists" signal; choose a threshold per use and validate it against ground truth. [Anderson]
14. **Stable IDs make external data attachable.** Give entities stable IDs (GERS), and where an ID must change, keep a traceable old→new mapping. Keep source IDs (OSM type+id, GTFS feed+stop_id). [Anderson; OSM relations; GTFS]
15. **Licences travel per layer.** ODbL (OSM-derived roads/buildings) requires share-alike for derivative databases; CDLA-Permissive (Overture places) does not. Check before commercial merging. [Anderson]
16. **Geocoding/matching = standardise → parse into components → compare against a reference → score → band.** Uppercase, canonical abbreviations, the same normaliser on both sides, locale-aware grammar, about ≥80 auto-accept / 60–79 review / <60 reject. [GeoMindz]
17. **Accuracy has several axes: resolution, positional accuracy against ground truth, and freshness.** Cost rises steeply with accuracy, so set the tolerance by the decision being made. [EagleView podcast]
18. **GTFS: only stops (and optional shapes) are geographic.** Mode lives on routes. Collapse platforms to `parent_station`, namespace IDs per feed, and expect blank interpolated times, times past 24:00 and calendar-only vs dates-only feeds. [ArcGIS GTFS]
19. **Geohash is a hierarchical string bucket, not a distance.** Prefixes nest, but neighbours across a cell edge can share no prefix, and cells shrink with latitude. Block on cell + 8 neighbours, then confirm with real distance; consider H3/S2 for more uniform cells. [O'Flaherty, with added notes]
20. **OSM features can be nodes, ways or relations.** Multipolygons and boundaries (incl. many airports and admin areas) must be assembled from member ways with roles (outer/inner), and tags sit on the relation. Extract all three types. [swroclawski]

## Jennings Anderson (Overture Maps Foundation) — Working With Overture Data: A Step-by-Step Guide (https://www.youtube.com/watch?v=NQ7A6gztGfo)
**Overture ships map *data* (not a map service) as cloud-hosted columnar files; you query the slice you need where it lives and download only that.**

(note: this is the Sept 2023 alpha webinar. Since then Overture moved to real GeoParquet, monthly releases, added addresses/base/divisions themes, and GERS IDs became UUID-style stable IDs rather than the H3-prefixed 128-bit design discussed here. Treat release numbers and schema details as historical; the workflow ideas still hold.)

- **Mental model.** Overture is a conflation layer *downstream* of sources (OSM, Esri Community Maps, Microsoft ML buildings, Meta/Microsoft places). It deliberately has no "download everything" button: the whole release was ~200 GB of Parquet on S3 and Azure Blob. The intended pattern is query-in-place (Athena/Synapse in cloud, DuckDB locally), filter by bbox/attributes, export to CSV/GeoJSON/shapefile/PMTiles.
- **Themes in the first release.** Admins (~100k features, admin level 2 = countries, level 4 = states/regions), buildings (785M; ~30M with height, ~10M of those from USGS lidar), places (~59M POIs from Meta + Microsoft), transportation (OSM roads re-segmented into *segments* and *connectors*, with connectors only where 2+ segments meet — i.e. a proper routable graph topology).
- **Building conflation order** is a priority stack: OSM first (human-validated), then Esri community data where OSM is missing, then Microsoft ML footprints as gap-fill. ML buildings accepted into OSM via RapiD become OSM and jump to top priority. Lesson: when conflating sources, make the precedence explicit and prefer human-validated over ML-derived; fixes should go upstream (to OSM) so they flow down.
- **Attribute-level provenance.** `sources` is an array that can say "footprint from OSM, height from USGS lidar". Worth copying in Sam's own master datasets: record source per attribute, not just per row, so later merges can be audited.
- **Places schema.** `names` object (common/official/alternate/short, each with value + language; `common` required), `categories` (main + alternate), websites/socials/emails/phones/brand, `sources`, a per-feature `bbox` struct, and geometry as WKB (convert to WKT with ST_AsText for humans).
- **Confidence score (0–1)** = confidence that the place *exists*. 0 means "we believe it no longer exists here" — a useful negative signal for matching, not just noise. Built mainly from social interaction signals (check-ins) and corroboration across sources; more sources ⇒ stronger scores. Distribution in that release: ~12% rounded to 1.0, ~14% each at 0.9 and 0.8. Overture ships all records and lets *you* pick the threshold (the demo used 0.8; a Kepler view looked clean at >0.98). Rule: pick a threshold per use case and validate it against ground truth in your region; keep low-confidence rows if you do entity matching.
- **Cheap spatial profiling.** Group features by zoom-8 web-map tile and count → instant global coverage map without downloading the dataset. Same trick split by source (share of OSM buildings per tile) reveals where ML gap-fill dominates. Directly reusable for checking GeoNames/OSM coverage per region before trusting a match.
- **Extraction recipe.** Filter on the bbox columns first (cheap, uses Parquet row-group stats), then refine with an exact predicate (ST_Contains with a polygon) — the classic two-stage filter. Export CSV → `ogr2ogr` to shapefile/GeoJSON → `tippecanoe` to tiles (PMTiles) for a web map. Large CSV points (200k) are slow in QGIS; convert to a real spatial format.
- **Cost/latency trade-off.** Athena bills per byte scanned but scans little thanks to columnar layout + bbox pruning; DuckDB is free but slower from a laptop because it must pull bits of many files designed for distributed readers. For Sam on 16 GB: DuckDB with bbox predicates against the remote Parquet, write only the regional extract locally.
- **Why not GeoParquet then:** their writer could not emit the GeoParquet metadata; also partitioning (by country? by tile?) is an "opinionated" choice that suits some uses and not others. Partitioning scheme is a real design decision for any spatial lake.
- **Licences are per layer and travel with the data.** Transportation and buildings carry ODbL (OSM-derived; derivative databases must be shared back), places carry CDLA-Permissive-2.0 (no share-back). Check before mixing into a commercial product — a Trameter dataset merged with ODbL layers may become a derivative database.
- **Stable IDs (GERS)** exist so third parties can attach data (traffic, ratings, bookings) to an Overture feature by ID instead of re-conflating geometry; plus linear referencing (OpenLR) for positions along road segments. Where an ID cannot stay stable it should be traceable across releases. Lesson for Sam: give master-location rows stable IDs and keep a change log mapping old→new when merges/splits happen.
- **Admins/addresses gaps (at the time):** only country and state levels; city boundaries and an address theme were on the roadmap. No Overture API planned — they expect others to build services on top.

## Max Gabrielsson (DuckDB Labs) with Mehdi Ouazza (MotherDuck) — The Journey of DuckDB Spatial Extension (https://www.youtube.com/watch?v=ZdcA4jViaaQ)
**DuckDB spatial fills the "too big for pandas, too small for a cluster" (~100 GB) middle ground with PostGIS-style SQL in an embedded engine.**

(note: recorded Sept 2024. The R-tree index, native GeoParquet read/write and `.method()` aliases were announced as imminent here and have since shipped; check current docs for exact behaviour.)

- **Problem it solves.** Teams with IoT/time-series or planet-scale OSM data hit a gap: Python/pandas/bash scripts break down, but Spark/distributed DBs need people and money they don't have. DuckDB (single-process, columnar, vectorised) targets that middle; the spatial extension brings geometry to it. The author came to geo by processing the OSM planet dump and terabytes of elevation rasters for a print-on-demand map side project — the pain was tools that do not scale to global data on one machine.
- **Design blueprint = PostGIS.** Function names and semantics follow PostGIS (the most complete open-source spatial SQL, ~20 years old, hundreds of functions), backed by the same libraries (GEOS for geometry ops, GDAL for file I/O, PROJ for reprojection). Divergence planned around projection handling and geodesic/spherical computation.
- **DuckDB-specific UX choices.**
  - Typed geometry columns in addition to generic GEOMETRY: e.g. `POINT_2D` has its own compact internal layout and specialised (faster) functions. Useful for millions of point rows such as GeoNames: a typed point column avoids the generic WKB overhead.
  - Functions accept DuckDB nested types: `ST_Collect` can take a LIST of geometries (row-wise) as well as acting as an aggregate.
  - Geometries print as WKT in the CLI, not hex WKB.
  - Function chaining (`geom.ST_Area()`), with planned shorter aliases (`poly.contains(pt)`) to avoid deep nesting.
- **Most common real use: ETL/conversion.** People use DuckDB spatial as a friendlier SQL front-end to GDAL instead of long `ogr2ogr` commands: read GeoJSON/shapefile/FlatGeobuf, clip, write another format. And as the easiest way to read big remote Parquet like Overture with one SQL query.
- **Use the database, not a zoo of files.** Analysts avoid databases as "too complicated" and end up with `clean_final_v3.csv` sprawl, losing transactions, durability, isolation, backups and normalised joins. DuckDB's single-file `.duckdb` format (stable since 1.0, no breaking changes) holds all tables. Rule: keep intermediate pipeline state in a DuckDB file; never use CSV for intermediate geo steps.
- **Spatial index (R-tree).** Before the index, any "give me everything in this box" was a full sequential scan, however fast. The R-tree index lets DuckDB traverse the tree, find matching row IDs and fetch only those from disk — quoted as roughly a 100x speed-up for selective geometry filters. Initially used only for filter predicates against a constant geometry, **not** for spatial joins (joins had their own strategy). Index matters mostly when geometries are stored in the DuckDB file format; previously people exported to FlatGeobuf or shapefile just to get a spatial index. An index also makes on-the-fly vector tile generation (`ST_AsMVT`) practical.
- **Why indexes are hard in an extension:** anything touching storage must cope with a DB opened without the extension loaded, or by a different extension version — so custom index types needed new core hooks.
- **GeoParquet.** It is a set of conventions + metadata on top of plain Parquet (geometry column as WKB, CRS, bbox stats), so any Parquet reader can read it with some decoding. Newer DuckDB with spatial loaded writes proper GeoParquet 1.0 metadata automatically when a table has a GEOMETRY column, and returns GEOMETRY directly on read (no manual `ST_GeomFromWKB`). GeoParquet 1.1 (native encodings, bbox covering column) support was pending.
- **Validity.** Simple-features invariants (e.g. holes must lie inside the outer ring) are not checked on every operation because that's expensive; invalid inputs give undefined results. Use `ST_IsValid` to audit and `ST_MakeValid` to repair before overlay/joins.
- **Extension loading.** `INSTALL` downloads once to the DuckDB home dir; `LOAD` is needed per session. DuckDB autoloads known extensions (httpfs, parquet, sometimes spatial) when it sees a matching function or file type, but explicitly `INSTALL spatial; LOAD spatial;` to be safe.
- **Demo pattern.** Read remote Parquet over HTTP (no download), build points with `ST_Point(lon, lat)`, filter by a bounding box in WHERE, display with lonboard (GeoArrow + WebGL, handles hundreds of thousands of points in a notebook; lighter than GeoPandas). ~1M rows took ~14 s from remote. When a source API accepts a bbox (Open Charge Map), push the filter server-side.
- **CRS handling gotcha.** At the time you juggled SRIDs yourself; the planned type-safe CRS was to prevent mixing projections or **swapping lon/lat order** — a classic bug: `ST_Point` takes x=lon, y=lat. For distances in metres either transform to a suitable projected CRS (`ST_Transform`) or use spheroid functions; beware that EPSG:4326 transforms can apply lat/lon axis order (use `always_xy` style options).
- **Rasters:** maintainer sceptical of raster-in-relational-DB; scripts with GDAL/Python usually beat PostGIS raster. A community PR for raster support existed but was not merged.
- **Relevance to Sam:** GeoNames 6M points + OSM extracts fit comfortably in a DuckDB file on 16 GB; build typed points, add an R-tree for repeated bbox lookups, write outputs as GeoParquet, and do conversions in SQL instead of shell pipelines.

## Patrick Dill & Brandon Marcellus (EagleView), AEC AI & Tech Strategy Podcast — Is Your Geospatial Data Accurate Enough? A Reality Check (https://www.youtube.com/watch?v=QMKTj_Q8Ypo)
**Accuracy is a cost curve: choose the resolution and freshness your decision actually needs, because past a point cost explodes.**

(note: vendor podcast, light on engineering detail and partly promotional; a mention of specific "frontier models" doing BIM is unverifiable chatter and is skipped.)

- **Mental model: the accuracy funnel.** Free satellite imagery answers many questions (e.g. vegetated vs bare ground — even 1960s satellites can tell that). Then aerial fixed-wing, then drone, then survey-grade reality capture (fractions of an inch). Each step down costs much more. Rule: state the question and required tolerance first, then buy the cheapest source that meets it.
- **Ground sample distance (GSD)** = ground size of one pixel; *lower is better* (counter-intuitive). Satellite: roughly 1 m and up (they quoted 12–14 in for good commercial satellite); fixed-wing aerial: ~6 in down to under 1 in (EagleView captures 1–2 in); drone: usually under 1 in. Practical effect quoted: measurement error goes from about ±5 ft with satellite to within inches with 1–2 in aerial. Lower GSD requires flying lower (3,000–15,000 ft for aircraft vs hundreds of miles for satellites; less atmosphere = more clarity).
- **Resolution ≠ positional accuracy.** Sharp pixels can still be in the wrong place. Absolute accuracy comes from georeferencing against surveyed ground control points; EagleView claims sub-1 ft absolute accuracy and ~1 month of post-processing QA (with a ~1 week early-access product for disaster response). Lesson for any dataset: ask for both the resolution/precision and the measured positional error against ground truth.
- **Obliques vs orthos.** Orthophotos (straight down, nadir) give 2D plan view; oblique captures at ~40° from four cardinal directions give height, overhangs, façade and roof assets — "the world is 3D". About 4x the information per location.
- **Freshness is part of accuracy.** A common failure: the free imagery predates the building/change you care about. Track capture date per tile/record; stale-but-sharp data is wrong data.
- **Modality by revisit need.** Need it tomorrow → drone. Several times a week → drone or satellite. Wide-area, high detail, periodic → aerial. On-site inspection is still required; imagery cuts rework and repeat visits (they cite a study claiming ~30% fewer site visits), and gives a single shared, consistent source across the team.
- **AI angle.** The value is in the underlying data and who controls it, not the model; vendors are exposing imagery via LLM tooling/MCP connectors and expect integration with BIM. "If they can't easily use it, they won't": make data easy to integrate.
- **Adoption advice (soft):** treat AI tools like interns you must give work daily; spend 15–30 min/day; add a personal "gate" asking how a tool could help before reacting by habit.
- **Relevance to Sam:** the same funnel applies to location data. GeoNames coordinates are often centroid-ish with unknown error; OSM varies by region; Overture places carry a confidence score. Define tolerance per use (city-level destination match may tolerate km; airport-to-terminal matching needs tens of metres), record source and date per record, and validate a sample against ground truth before trusting a threshold.

## Matt Forrest — Why Apache Sedona Might Replace Half Your Geospatial Stack (https://www.youtube.com/watch?v=VXCD8ifN4Oc)
**Sedona is "PostGIS for Spark": reach for it only when PostGIS/DuckDB/GeoPandas genuinely hit a wall on volume or complexity; otherwise its overhead makes it slower.**

(note: the video blends three products: Apache Sedona on Spark, the newer single-node SedonaDB (Rust), and Wherobots, the commercial cloud from Sedona's creators, which the presenter promotes. Treat the 1–5 ratings as opinion.)

- **What it is.** Formerly GeoSpark. Spark splits a job into partitions processed in parallel across workers ("assembly line"). Sedona adds geometry and geography types, raster types, and 300+ `ST_` / `RS_` functions to Spark SQL and PySpark — close to PostGIS coverage. Also runs with Flink, Snowflake and others. Python mental model: GeoPandas + Rasterio for data that does not fit one machine.
- **Compute separate from storage.** It reads shapefile, GeoJSON, CSV, Parquet/GeoParquet, Cloud-Optimized GeoTIFF, NetCDF from local disk or object storage without first copying everything, and writes cloud-native outputs (GeoParquet, COG) at scale — one of the most efficient ways to *produce* big GeoParquet datasets.
- **"Scale" has two axes.** Row/byte volume, and *operation complexity*: area-weighted interpolation (split polygons by overlap and re-aggregate), zonal statistics (raster × vector). Complex overlays are where DuckDB, plain Python and even PostGIS show cracks first. Raster+vector in one distributed engine is unusual; data warehouses handle vector only.
- **Decision rule.** Use what you have (GeoPandas/PostGIS/DuckDB) until runs take unreasonably long or crash — the point of diminishing returns. For small/medium data, Spark's startup and shuffle overhead often makes Sedona *slower*. SedonaDB is the middle option: single node, pip install, no cluster. Ratings given: personal/one-off projects ~3.5, small teams ~4, enterprises ~4.5 (only if you actually have the scale problem).
- **Mechanisms to understand.**
  - *Partitioning*: how data is split across workers; for spatial data you want spatially coherent partitions so joins don't compare everything with everything.
  - *Broadcast joins*: for lopsided joins (a few hundred polygons vs a billion points), send the small side whole to every worker instead of partitioning it. This is directly the pattern for Sam's "few thousand destinations/airports vs millions of points" joins in any engine.
  - Spark UI to watch jobs; memory configuration is its own discipline.
- **Costs & pitfalls.** Requires Spark knowledge; tuning clusters is real work. A running cluster bills by time (unlike pay-per-query warehouses) — test locally first, then lift-and-shift the same code to EMR, Databricks, Kubernetes or Wherobots. Raster support is good for resampling/aggregation/map algebra but not a full GDAL/xarray replacement; for heavy raster ML use xarray, Rasterio, TorchGeo.
- **When not to use it.** Small/medium data; interactive editing or cartography (it is a backend batch engine — use PostGIS behind QGIS); teams with no Spark experience where the learning curve outweighs gains.
- **Fits** mobility/movement traces, remote sensing, climate, IoT; integrates with Iceberg tables, warehouses, ML pipelines (feature prep for GeoAI/LLMs).
- **Relevance to Sam:** on a 16 GB laptop with GeoNames (~6M) and regional OSM extracts, DuckDB/GeoPandas are the right default; Sedona/SedonaDB becomes interesting only for planet-scale OSM/Overture joins or heavy polygon overlays. Borrow the broadcast idea regardless: keep the small side (destinations/bboxes) in memory and stream the big side in chunks.

## Matthew Hanson (Element 84), FOSS4G 2022 — The State of Cloud-Native Geospatial (https://www.youtube.com/watch?v=xtK_gbxZdRk)
**Cloud-native geo = searchable metadata (STAC) + data cut into small addressable chunks, so any client can find and read exactly the piece it needs — an open, standards-based Google Earth Engine.**

- **Goal: a "queryable Earth."** Users ask "how many ships in this port?", "how many buildings went up here?" — never "give me MODIS scene X." Data sources are an implementation detail; architecture should hide them. Earth Engine proves the UX (script → global mosaic, no scene handling) but is closed, non-standard, not self-deployable, hard to extend. Cloud-native geo rebuilds that with open specs.
- **Reproducibility motive.** "Executable papers": a button that opens the analysis in your own cloud account against the same data. Many studies cannot be reproduced because data is hard to fetch scene by scene.
- **Discovery problem.** Public buckets (AWS Open Data) often force you to *construct file names* from tile IDs/dates to find data — and the tile may not even cover your area of interest, so you download nothing useful. With archives like NASA's (>250 PB projected; NISAR ~85 TB/day downlink), unindexed metadata means the data effectively doesn't exist. Click-to-download geoportals are fine for demos, terrible for data science.
- **STAC (SpatioTemporal Asset Catalog)** — started 2017. Requirements: easy search/discovery, reuse existing standards, don't replace existing metadata standards, *crawlable* (static JSON files work with no server; crawl and index into a DB if you want search), small stable core + extensions.
  - Hierarchy: Catalog (container) → Collection (a product, e.g. Landsat, Sentinel-2) → Item (one place + one time, a GeoJSON Feature) → Assets (the actual files). `links` give parent/collection/root navigation plus docs/DOI/code.
  - STAC API builds on OGC API – Features with cross-collection search endpoints.
  - Extensions are a marketplace: anyone can publish one; core-only clients still work; useful ones (projection, raster, EO bands, SAR) become best practice.
  - Static catalogs often partition by tile/year/month; an API makes sub-catalogs unnecessary because you search instead.
- **What makes a format cloud-optimized: small addressable chunks.** Default GDAL rasters are stored in strips, each compressed separately; to read a small AOI you must fetch and decompress whole strips. A COG stores internal tiles (plus optional overviews) and an index so an HTTP range request reads only the tiles you need. Zarr goes further: each chunk is its own object ("exploded" format). Overviews are nice but not the essence.
  - Legacy NetCDF/HDF can become cloud-readable without conversion by generating a sidecar index of chunk byte offsets (kerchunk). Even a "cloud-optimized tar" exists (sidecar index into a tar).
  - The real scaling win is parallelism: many Dask workers each read different chunks of the same file at once (xarray + Dask). odc-stac turns a STAC search directly into an xarray, replacing Open Data Cube's Postgres dependency.
- **Why some specs become standards:** adoption and a software ecosystem feed each other; bootstrap with outreach and open-source tooling. Handing people a spec alone fails. STAC/COG won because usable catalogs (Sentinel, Landsat) and tools existed early. Examples: Element 84 Earth Search, USGS Landsat STAC, Microsoft Planetary Computer (best open analogue of Earth Engine), stacindex.org, stac-utils org, pystac-client. Even USGS astrogeology uses STAC for Mars/Jupiter data.
- **Stop thinking in files; write algorithms over metadata.** The classic science folder full of `final_final_v2` files has no provenance. Instead a step takes STAC Item(s) in (which fully describe data and where/how to access it), fetches only what it needs, and emits a new/modified Item with lineage, source item and version recorded. Lightweight, traceable, cloud-friendly.
- **Closing rule:** if you build services, build them on top of a cloud-native layer where the service reads the data directly.
- **Relevance to Sam:** even for vector pipelines (GeoNames, OSM, GTFS feeds), keep a small catalog/manifest per dataset run (source URL, snapshot date, bbox, version, parent run) and write chunked/partitioned outputs (GeoParquet with row groups) rather than ad-hoc CSV files. This gives provenance and lets DuckDB read only the needed chunks.

## GeoMindz.com — Geocoding: Address Standardization (https://www.youtube.com/watch?v=sVRHPVJZE8Q)
**Geocoding is not a lookup table of every address string; it parses the input into standard components, normalises them, matches each component against a reference layer, and scores the match.**

- **Why it's hard.** Addresses are made for humans, who silently forgive variants ("375 Oak Road", "375 Oak Rd", "375 N Oak Rd", "375 Oak") and even errors ("Oak Street" when it's Oak Road). Computers are literal. A table of every address × every spelling variant is infeasible, so geocoders standardise first. Coordinates, by contrast, are easy to plot.
- **Locale matters.** Address grammar differs by country; the US model below doesn't transfer. Use country-aware parsers/geocoders (note: libpostal is the usual open-source answer for international parsing/normalisation; Nigerian addresses, for example, often rely on landmarks rather than house numbers).
- **Pipeline.** (1) standardise/parse the input string; (2) compare each component with attributes of a *reference layer* (a specialised vector dataset — street centrelines with address ranges, parcels, or address points; covered in the next lecture); (3) produce a match score, typically 0–100.
- **US component model:** house number; prefix direction (N in "N Oak Rd"); prefix type ("Highway" in "Highway 85", "Interstate" in "Interstate 85" — the number is then the street *name*); street name; street type (St, Rd, Ave, Blvd, Ct, Cir…); suffix direction ("Palm St E"); ZIP code (a strong locator). Worked examples: "27 Middle St N" → suffix dir N; "971 Highway 85" → prefix type HWY, name 85; "429 E St Alaric St" → prefix dir E, name "ST ALARIC", type ST.
- **Normalisation rules.** Uppercase everything (case carries no location meaning; avoids case-sensitive comparison bugs). Map words to a canonical abbreviation list (STREET→ST, ROAD→RD, NORTH→N) — the same canonical forms the reference layer uses. Watch ambiguous tokens: "St" can be Saint (part of the name) or Street (type); position in the string decides.
- **Score bands as a review policy.** ~80–100: confident, auto-accept. ~60–79: plausible, send to review or accept depending on the use. <60: treat as unmatched. Thresholds depend on purpose; keep the score on every row.
- **Rules of thumb.** Normalise both sides (input and reference) with the *same* function. Parse into fields before fuzzy matching so you compare like with like (name vs name, type vs type). Expect typos and wrong types; reward matches on strong fields (number, name, postcode) more than weak ones (type, direction).
- **Relevance to Sam:** the same standardise→component-match→score→band approach is exactly what place/destination matching needs: uppercase/strip accents (unidecode), canonicalise tokens ("Intl"/"International", "St"/"Saint", "Apt"/"Airport"), split name from type words ("X Bus Station", "Ferry Terminal X"), match on name + country/admin + distance, store a 0–100 score with auto-accept / review / reject bands.

## Matthew Hanson (Element 84), FOSS4G 2023 — An Overview of Cloud-Native Geospatial (https://www.youtube.com/watch?v=g7iMO1KmyJE)
**The open-source world has rebuilt each component of Google Earth Engine — discovery, orchestration, scalable file access, analytics, visualisation — as separate interoperable standards and tools.**

(Overlaps heavily with his 2022 talk above; only new material is noted in depth.)

- **Earth Engine decomposed (2010 onward):** unified data discovery → STAC + OGC API – Features; orchestration/ingest → Airflow, Prefect, Planetary Computer's PC Tasks, Element 84's Cirrus (AWS Step Functions + DynamoDB) and SWOOP (STAC Workflow Open Orchestration, exposed via OGC API – Processes); scalable file access → COG, Zarr/GeoZarr, COPC, GeoParquet, kerchunk; scalable analytics → Pangeo (xarray + Dask from a thin Jupyter client), odc-stac; visualisation → dynamic tiling servers (e.g. TiTiler) over blob storage. Assembled: Microsoft Planetary Computer; FilmDrop (Element 84's deployable "own Earth Engine").
- **STAC vs OGC API – Features (the frequent question).** Ask: *is the geometry the data, or metadata about where data is?* If the geometry *is* the data (buildings, roads, POIs, ML training labels) → Features API / vector format. If the geometry is just the footprint of separate asset files (scenes, tiles) → STAC. Shoe-horning labels or vector features into STAC (the label extension) is possible but usually the wrong fit. For Sam: places/airports/terminals are features, not STAC items; STAC would only describe the dataset *files*.
- **Metadata is the atomic unit of processing.** Workflows take STAC in and emit STAC out, adding assets or new items, recording `derived_from` links and processing version for provenance. Explicit warning: don't encode metadata (dates, versions) in file names and expect it to persist.
- **Three ingredients of most cloud-optimized formats:** (1) an easy-to-reach table of contents (header or sidecar) telling where each chunk lives; (2) internal tiling/chunking instead of strips; (3) overviews (pre-computed lower resolutions). Tile size has no universal answer — align it with typical AOIs and with how work is split among workers. Core definition again: small addressable chunks.
- **Zarr trade-off.** Each chunk is a separate object → great parallel reads, but every object is an API call, so *moving or deleting* a big Zarr store costs huge numbers of requests. Sharding (re-grouping chunks into files) was being developed — converging back towards the HDF model. Zarr grew from climate modelling where grids are global lat/lon arrays with no affine transform/projection (effectively coordinates per pixel); GeoZarr (OGC working group, based on CF conventions) adds GDAL-style geo-awareness.
- **COPC** (Cloud-Optimized Point Cloud) applies the same idea to lidar; QGIS can now visualise point clouds natively.
- **GeoParquet** (then 1.1.0 beta) aims not to be "yet another standard" but simply the agreed way geometry is encoded inside Parquet, so geometry becomes just another column type.
- **Kerchunk** makes legacy formats (NetCDF, HDF, even tarballs) cloud-readable by generating a sidecar table of contents, no conversion needed.
- **Community:** Cloud-Native Geospatial Foundation (Radiant Earth), cloudnativegeo.org.
- **Rules:** chunk data for the access pattern; keep a table of contents/index; consider object count when choosing many-small-files layouts (also true for over-partitioned Parquet: thousands of tiny files are slow to list, move and query).

## Kyle Barron (Development Seed), Cloud-Native Geospatial Forum — Why GeoParquet (https://www.youtube.com/watch?v=KWQMa-y8CNg)
**GeoParquet = columnar, row-grouped, compressed vector data whose footer metadata lets readers fetch only the columns and row groups they need — but spatial pruning only works if you *sort* the data spatially.**

- **Versions.** 1.0 (Sept 2023); 1.1 (June 2024) added the bbox "covering" column for spatial partitioning and native GeoArrow geometry encodings (alongside WKB).
- **Three reasons it matters:** (1) cloud-native — readable remotely without full download; (2) fast and small even locally; (3) pairs with GeoArrow for zero-copy in-memory interop.
- **Mechanism.** Parquet stores data in *row groups* (e.g. ~100k rows each); within each, each column is a separate compressed chunk. Footer metadata lists every row group's byte offsets and per-column min/max statistics. A reader fetches the footer, then issues HTTP range requests only for the needed columns (column pruning) and row groups (predicate pushdown). Engines do this automatically.
- **Spatial partitioning vs spatial indexing (key distinction).** GeoPackage/FlatGeobuf hold a per-row spatial index — great for pulling a handful of features fast. GeoParquet stores spatial info only per *row group* (bbox covering column → min/max of xmin/ymin/xmax/ymax per group). That is coarser but scales far better for analytical, billions-of-rows data. The spec does not mandate a sort method (Hilbert curve, geohash/S2/H3 order, admin region…); you choose, metadata stays standard. Groups can be within one file or across many files — equivalent idea.
- **Gotcha (stated as most important):** writing the bbox column is *not enough*. If rows are in random order, every row group's bbox spans the whole world and pruning skips nothing. Sort spatially (e.g. `ORDER BY ST_Hilbert(geom)` or by geohash/quadkey) before writing. Few tools did this automatically at the time (Sedona, Fused cited; GDAL writes the covering bbox and may sort).
- **Demos.** Overture's explorer renders fast from **PMTiles** (pre-built vector tiles; overviews) but "download visible" reads GeoParquet directly in the browser via WebAssembly (~10 s for a viewport; first load slow because it reads footers of ~200 files). In Python (geoarrow-rs, Rust under the hood): open the ~200-file Overture buildings dataset (~2.4 B rows), pass a bbox *in the data's CRS*, get the matching table in ~9 s; render with lonboard. Locally, a 3M-point GeoParquet loaded in ~0.8 s and rendered in ~0.8 s.
- **Size/speed:** his benchmarks showed GeoParquet with ZSTD compression smaller than other vector formats and usually faster to read and write.
- **GeoParquet vs GeoArrow:** Parquet = on-disk format; Arrow = in-memory columnar format. Loading GeoParquet into GeoArrow gives a table you can hand zero-copy to Polars, DuckDB, pandas, PyArrow; GDAL's Arrow interface speeds up GDAL bindings too.
- **Visualisation vs analysis.** GeoParquet has no overviews/generalised levels; pair it with PMTiles for display and use GeoParquet for compute.
- **Streaming caveat.** Metadata lives in the footer, so true streaming is impossible; readers fetch footer first then batches (async iterator of batches) — range requests beat streaming anyway.
- **Rules for Sam:** store GeoNames/OSM/terminal outputs as GeoParquet with ZSTD; sort by a space-filling curve before writing; keep row groups ~100k–1M rows; include bbox columns; then DuckDB queries with a bbox predicate read only a fraction of the file — a big win on 16 GB RAM. Keep a lon/lat CRS (EPSG:4326) consistent with your query bboxes.

## Jonathan Soma — Spatial joins in GeoPandas (https://www.youtube.com/watch?v=y85IKthrV-s)
**A spatial join is a normal table join whose key is a geometric relationship instead of a shared column; the left table's geometry is kept and the right table's attributes are attached.**

(note: 2019 video. In current GeoPandas the `op=` argument is `predicate=`; also see `sjoin_nearest` for nearest-neighbour joins.)

- **Mental model.** Column join: A + B on a common key (ZIP). Spatial join: A + B on a spatial relationship (point *within* polygon, line *intersects* polygon…). Classic use: tag points with the polygon they fall in (power plants → state, restaurants → neighbourhood, airports → country/admin region).
- **API anatomy:** `gpd.sjoin(plants, states, how="inner", predicate="within")`.
  - *Order matters:* the left frame's geometry is kept (plants stay points); the right frame contributes its attribute columns (name, population) but not its geometry, plus an `index_right` column pointing back to the matched polygon row.
  - *how:* `inner` drops left rows with no match (points at sea / abroad); `left` keeps them with nulls. In the demo 7,610 plants → 7,410 with inner (200 had no state); left kept all 7,610.
  - *predicate:* `within` for "point inside polygon"; others include intersects, contains, touches, crosses.
- **CRS check first, every time.** Plants were EPSG:4326 (WGS84 lat/lon) and states EPSG:4269 (NAD83) — "slightly different" assumptions about the Earth. GeoPandas refused the join until both matched; fix with `states = states.to_crs(plants.crs)` (either side can be converted). Rule: assert `a.crs == b.crs` before any spatial comparison. (note: NAD83 and WGS84 differ by ~1–2 m in North America; other datum mismatches or a projected-vs-geographic mismatch are far worse — silently wrong answers.)
- **Aggregations fall out naturally.** Once each point carries the polygon's name, counting per polygon is just `value_counts()` on that column (e.g. ~1,200 plants in California, 460 in North Carolina); filter first for subsets (coal plants: Pennsylvania 24 first). You don't need to join the other way round to count.
- **Limitation:** the result keeps point geometry, so to draw a choropleth you must aggregate and merge counts back onto the polygon frame (column join on name/ID).
- **Gotchas:** a point on a shared border or polygons that overlap can match multiple rows → duplicated left rows; check `len(result)` vs `len(left)` with a `left` join and deduplicate deliberately. Points falling in no polygon (coastline generalisation, offshore airports/ferry terminals) vanish with inner joins — use left and inspect the nulls; consider nearest-polygon fallback with a distance cap.
- **Relevance to Sam:** assigning GeoNames points, airports or GTFS stops to countries/admin areas is exactly this pattern. Use `how="left"`, a valid-geometry polygon layer, matching CRS, and on 16 GB process the point side in chunks against an in-memory polygon frame (GeoPandas builds an STRtree on the right frame automatically).

## ArcGIS (Esri) — Introduction to GTFS (https://www.youtube.com/watch?v=8OQKHhu1VgQ)
**GTFS is a zip of CSV tables linked by IDs; only `stops` (and optional `shapes`) carry geography — routes and trips are categories, and schedules live in `stop_times` + calendars.**

- **What it is.** The only worldwide standard for public-transit schedule data: stops, lines, schedules. Comma-delimited text files with a fixed schema, related by ID fields; some files required, some optional, so not every feed has every file.
- **Geographic/structural files.**
  - `stops.txt`: `stop_id`, `stop_lat`, `stop_lon`, `location_type` (0 ordinary stop/platform, 1 station, 2 entrance/exit, 3 generic node, 4 boarding area), `parent_station` (stop inside a larger station), `wheelchair_boarding`. **For Sam's terminal dataset this hierarchy is critical:** collapse child platforms/entrances to their `parent_station` to get one terminal per station; stops with `location_type=1` are the stations themselves; entrances (2) and generic nodes (3) are not boarding points.
  - `routes.txt`: what riders think of as a line ("Bus 10", "Yellow Line"). Not geographic — a category; can branch and cover both directions. `route_id`, and `route_type` = mode (tram, subway, rail, bus, ferry, cable car, gondola, funicular… — note: extended route types in the 100–1700 range also appear in European feeds). Mode is assigned at *route* level, so to know a stop's modes you must join stops → stop_times → trips → routes.
  - `trips.txt`: one vehicle run of a route with a fixed stop sequence and times on a service pattern. Fields: `trip_id`, `route_id`, `shape_id`, `service_id` (→ calendars), `wheelchair_accessible`, `bikes_allowed`. Also non-geographic.
  - `shapes.txt` (optional): the path vehicles travel, as ordered lat/lon points per `shape_id`; one route can have several shapes (each branch × direction). Purpose is visualisation, not analysis; often messy because derived from noisy vehicle GPS. Without it you can only draw straight lines between consecutive stops (Esri offers tools to estimate on-street paths with Network Analyst).
- **Schedule files.**
  - `calendar.txt`: regular weekly service per `service_id` (monday…sunday flags, `start_date`, `end_date`).
  - `calendar_dates.txt`: exceptions, adding or removing service on specific dates (holidays). Both optional but at least one required; some feeds use only calendar, some define *everything* as dated exceptions — both valid, so inspect before assuming.
  - `stop_times.txt`: every visit of a trip to a stop — `trip_id`, `stop_id`, `stop_sequence`, `arrival_time`, `departure_time`, `shape_dist_traveled`. Times may be blank for non-timepoint stops (valid; must be interpolated for analysis). (note: GTFS times can exceed 24:00:00 for after-midnight trips of the previous service day — don't parse them as clock times.) This is usually the biggest file by far.
  - `frequencies.txt` (optional): compact headway-based service (time window + headway) for repeating patterns, used with stop_times.
- **Third-column files** (agency, fare, transfers, feed_info, etc.) mentioned but not covered.
- **Rules for Sam:** read feeds with explicit dtypes (IDs as strings; leading zeros matter); IDs are only unique *within a feed*, so namespace them with a feed ID when merging many feeds; derive per-stop mode sets via the route join; use `stop_times` counts / calendar to filter out stops with no active service; be wary of feeds with expired calendars; stream `stop_times` in chunks or query it with DuckDB directly from the CSV on a 16 GB machine.

## Jim O'Flaherty (QA Locate) — Geohash: Deep Intuitive Understanding in under 7 Minutes (https://www.youtube.com/watch?v=UaMzra18TD8)
**A geohash is a base-32 string naming a lat/lon rectangle; each extra character subdivides it 32 ways, so a shared prefix means a shared parent cell.**

- **Origin.** Invented by Gustavo Niemeyer in 2008, public domain.
- **Mechanism.** The world is split into 32 cells (8 wide × 4 tall at the first level), labelled with 0–9 and letters excluding a, i, l, o (the video says "minus a, i, l" — note: the standard alphabet omits a, i, l, o). Each cell splits again into 32: grids alternate 8×4 and 4×8, so odd-length hashes are roughly square and even-length ones are 2:1 rectangles (bits alternate longitude/latitude). Example in Las Colinas, Texas: `9vgv1egd4` sits inside `9vgv1egd`, inside `9vgv1eg`… ("reverse telescoping").
- **A geohash is an area, not a point.** It is defined by its four corners; its centre point is used when you need a coordinate. Precision grows with length: 9 characters ≈ 4.8 m square; 11 characters ≈ 15 cm (6 in), "good enough to call a point"; up to ~19 characters reaches nanometres (useless in practice). (note: rough cell widths at the equator: 5 chars ≈ 4.9 km, 6 ≈ 1.2 km, 7 ≈ 153 m, 8 ≈ 38 m; cells shrink east–west with latitude.)
- **Why use it.** A single string column instead of two floats: databases index and prefix-query strings cheaply (`LIKE '9vgv1%'`), giving a cheap spatial bucket/join key and a sort order with locality (Z-order curve).
- **Gotchas not covered in the video, but critical (note):** (1) edge effect — two points metres apart across a cell boundary can share no prefix (worst at the equator/prime meridian/antimeridian splits), so proximity search must also check the 8 neighbouring cells; (2) cells are not equal-area — they get narrower towards the poles, so a fixed precision means different ground distances by latitude; (3) prefix match ≠ distance; always confirm with a real haversine distance. For equal-ish area hierarchical cells use H3 (hexagons, uniform neighbours) or S2 (sphere-aware, better near poles).
- **Relevance to Sam:** geohash (precision 5–6) is a good blocking key for matching GeoNames/OSM/airport candidates: join on cell + neighbours, then score by distance and name. It is also a simple sort key before writing GeoParquet.

## swroclawski — OpenStreetMap Basics: Relations (https://www.youtube.com/watch?v=OIYAgA2EGS0)
**Relations are OSM's third element type: tagged, ordered groups of nodes/ways/relations where each member has a role — used for anything a single way can't express, such as polygons with holes.**

- **OSM data model recap.** Node = point with tags (and lat/lon). Way = ordered list of nodes; a line, or an area when closed. Relation = a group of members (nodes, ways, or other relations) that describes a relationship. Every element has an ID, unique within its type (node 50 and way 50 are different objects).
- **Relation anatomy.** A `type=*` tag says which kind of relation it is (multipolygon, route, boundary, restriction…). Each member has a *role* describing its part in the relation.
- **Worked example: building with a courtyard** (common in European blocks). Outer outline way 50, inner courtyard way 51. A single closed way can't have a hole, so create a relation tagged `type=multipolygon` + `building=yes`, members way 50 role `outer`, way 51 role `inner`. The feature tags go **on the relation**, not on the ways.
- **Gotchas for data engineers (note: beyond the video):** to get the geometry of a multipolygon or boundary you must *assemble* it from member ways (and their nodes) — tools like osmium, pyosmium, osm2pgsql, QuackOSM/DuckDB do this. Countries, admin boundaries, large lakes, airports (`aeroway=aerodrome` mapped as multipolygons), and transit routes (`type=route`, `route=bus/ferry`) are relations; filtering only nodes and ways misses them. Broken/incomplete relations (members outside your extract) yield invalid or missing polygons — use extracts that keep complete relations. A feature can be mapped as a node, a way or a relation, so POI extraction should take all three and represent areas by centroid or point-on-surface.
- **Relevance to Sam:** when pulling airports, stations, ferry terminals or admin areas from OSM, include relations and assemble multipolygons; keep the OSM type+ID (e.g. `r123`, `w50`) as the stable source key.
